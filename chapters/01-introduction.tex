\chapter{Introduction}\label{ch}

Applications distributed across graphics processing units (GPUs) must coordinate data movement as well as computation. When an application uses multiple GPUs within a node or across nodes, its communication stack determines how transfers are initiated, progressed, and completed, and how they interact with GPU kernels. Selecting a suitable stack therefore requires understanding both the application's communication needs and the execution costs of the available implementations.

This thesis investigates that selection problem through a progression from communication patterns to a complete application. A common benchmark identifies the regimes in which different stacks are effective; extensions to oneCCL examine how additional communication paths can be exposed through a shared interface; and an extended Conjugate Gradient (CG) solver tests whether the benchmark guidance transfers to application execution. This chapter develops the motivation and research gaps behind that progression, defines the research questions, and summarizes the scope, findings, and contributions.

\section{Selecting Communication Stacks for Distributed GPU Applications}

GPUs provide the parallelism and memory bandwidth used by scientific simulations and large-scale artificial-intelligence workloads. Distributing these workloads introduces communication with different performance requirements: sparse solvers exchange boundary values and reduce scalar dot products, while distributed training combines gradients or redistributes activations. Scalability depends on the cost of these operations and on whether their dependencies leave communication exposed on the application's critical path \cite{unat_landscape_2026,choi_end--end_2020}.

Even when a transfer accesses GPU memory directly, the CPU may still issue the operation, wait for a producing kernel, and arrange completion before the next kernel starts. Repeated host orchestration can leave devices idle or prevent useful overlap. Moving communication calls into GPU kernels can reduce this overhead, but a host-driven library can remain efficient when its algorithms, batching, and progress mechanisms match the workload \cite{unat_landscape_2026,agostini_gpudirect_2018}.

Several programming models and libraries address these requirements. MPI provides a portable interface for distributed-memory point-to-point and collective communication. GPU-aware implementations accept device buffers, removing explicit host staging from application code and permitting direct GPU data movement. The implementation may still stage internally, depending on the operation, transport, and topology.

Vendor-optimized collective libraries, such as NVIDIA NCCL and AMD RCCL, provide specialized implementations of operations such as all-reduce, broadcast, reduce-scatter, and all-gather. These libraries are particularly important in distributed deep-learning workloads, where collective operations frequently dominate communication time \cite{weingram_xccl_2023}. Their performance depends on several internal decisions, including the selected communication algorithm, transport protocol, number of communication channels, and underlying system topology \cite{hu_demystifying_2025}.

A different approach is provided by one-sided Partitioned Global Address Space (PGAS) models such as OpenSHMEM. GPU-oriented implementations, including NVSHMEM and ROC\_SHMEM, extend this model by allowing communication operations to be initiated directly by GPU threads or thread blocks. Device-initiated communication can reduce CPU involvement and enable fine-grained communication from inside a kernel, potentially improving overlap and reducing synchronization overhead \cite{agostini_gpudirect_2018,ma_demystifying_2026}. Portable implementations such as OSHMPI instead provide OpenSHMEM semantics over MPI. These alternatives make different trade-offs: symmetric-memory requirements, synchronization semantics, message granularity, host involvement, and implementation maturity can all determine whether one-sided communication is beneficial.

These alternatives create a practical selection problem. The relevant input is the application's \emph{communication signature}: its operations, message sizes, peer sets, synchronization points, rank placement, and opportunities for computation--communication overlap. Recent studies show that default collective configurations can be substantially slower than choices made for a particular topology and workload \cite{pasqualoni_pico_2026,li_tuccl_2025}. Both the backend and its configuration therefore belong in the selection process.

Vendor-specific ecosystems generally provide highly optimized implementations, but they couple applications to a particular hardware and software stack. SYCL and oneCCL provide source-level abstractions that reduce this coupling. Source portability, runtime backend interchangeability, and performance portability are nevertheless distinct properties: a common interface may add orchestration, staging, or synchronization costs, and measurements on NVIDIA A100 GPUs cannot by themselves establish cross-vendor performance portability \cite{hammond_comparative_2019,shen_sycl_2026}. This thesis therefore treats CUDA and SYCL variants as concrete implementation stacks and supporting controls, rather than making cross-vendor portability a separate experimental claim.

\subsection{Research Gap and Approach}

Prior work already connects communication mechanisms to applications. Agostini et al. examine GPUDirect Async through microbenchmarks, modeling, and application cases; PICO assesses benchmark-informed choices through simulated training-trace replay; TuCCL reports end-to-end training improvements; and Trotter et al. compare host- and device-initiated CG solvers \cite{agostini_gpudirect_2018,pasqualoni_pico_2026,li_tuccl_2025,trotter_cpu-_2025}. Building on these studies, this thesis investigates three connected questions left open for the selected stacks and application:

\begin{itemize}
\item \textbf{Comparable characterization across communication stacks.}
Separate library benchmarks do not establish how the selected MPI, collective-library, and SHMEM paths rank under a shared measurement policy. A common CUDA/SYCL harness makes it possible to locate favorable performance regimes while recording the memory, completion, and progress differences that qualify the comparison.

\item \textbf{Performance and integration costs of SHMEM-style communication.}
Direct SHMEM measurements do not establish how much performance survives the buffer and completion adaptations required by a common interface. Comparing NVSHMEM and OSHMPI with MPI and NCCL exposes their direct trade-offs; implementing the missing paths in the oneCCL source used for this work exposes the integration requirements. Grouped NCCL support and a complete OSHMPI backend provide executable comparison paths, while a separately validated NVSHMEM runtime foundation establishes the prerequisites for a further backend.

\item \textbf{Transfer from communication patterns to solver execution.}
It remains to be established which observations from this comparison predict application performance once irregular peers, computation, and convergence are included. Extending the published CUDA/HIP aCG suite with an OSHMPI communicator enables that test for an additional one-sided halo path. A SYCL implementation supports a subsidiary investigation of how much native CUDA solver performance a portable implementation retains on the same platform.
\end{itemize}

\begin{keypoint}[Central proposition]
Persistent device work can amortize host-control costs, but memory placement, completion semantics, and progress determine the favorable regimes. Pattern-oriented measurements can guide backend selection when the application's peer structure and dependencies preserve those regimes.
\end{keypoint}

The benchmark consequently covers reductions, neighbor exchanges, and all-to-all redistribution, with point-to-point tests as a transfer reference. Iterative sparse solvers motivate small reductions and halo exchanges; distributed training motivates bulk reductions; and Mixture-of-Experts routing motivates uniform and variable-count redistribution. The application study validates the reduction and halo families through aCG.

\section{Research Questions}

Selecting a communication stack begins with a practical uncertainty: when does moving communication calls into a GPU kernel repay the cost of changing the execution path? A host-driven application may repeatedly wait for a producing kernel, submit a transfer, and establish completion before computation can continue. Persistent device execution offers a way to keep this sequence on the GPU, but introduces its own synchronization and progress requirements. The first step is therefore to locate the message sizes and placements at which the balance changes. The persistent NVSHMEM ping-pong and halo kernels provide this evidence at pattern level, while the monolithic NVSHMEM solver extends the investigation to repeated application execution. Because these paths also differ in algorithms and organization, the comparison concerns the benefit of each complete stack.

\begin{researchquestion}[RQ1 -- Conditions for beneficial GPU initiation]
Under which evaluated configurations do persistent NVSHMEM ping-pong and halo kernels and the monolithic NVSHMEM aCG solver outperform host-initiated alternatives? What evidence supports launch, synchronization, or proxy-progress costs as explanations for the observed message-size and scaling boundaries?
\end{researchquestion}

A favorable timing is only the beginning of an adoption decision. To use a SHMEM path, an application must establish suitable memory, identify remote destinations, and coordinate completion and buffer reuse. NVSHMEM and OSHMPI expose these responsibilities through different execution and progress mechanisms. Adopting them beneath oneCCL adds another requirement: the adapter must reconcile those mechanisms with ordinary application buffers and an event-based interface. Staging or blocking synchronization may consume part of the advantage observed in a direct benchmark. The second question consequently asks what the measured performance requires from the programmer and runtime, and how those requirements change when communication is exposed through a common interface.

\begin{researchquestion}[RQ2 -- Practical trade-offs of SHMEM-style communication]
How do the evaluated NVSHMEM and OSHMPI paths compare with MPI and NCCL in performance and programming requirements? What memory, ordering, completion, and progress adaptations are required beneath oneCCL, and what costs are measured for the completed adapters?
\end{researchquestion}

The next step is to put the candidate paths back into an application. In a CG solver, halo data arrives from an irregular set of peers, local matrix--vector work may hide part of the transfer, and small global reductions can delay the next update. A path that wins an isolated exchange may therefore contribute little to solver performance, while a modest reduction-latency improvement may matter on every iteration. Moving from individual patterns through the composite CG step to complete aCG execution tests which benchmark observations remain useful once these dependencies and convergence are included.

The application also makes the portability question concrete. Expressing the solver through SYCL changes kernels, memory handling, and host orchestration alongside the available communication interfaces. The final question therefore combines the main test of benchmark-to-application transfer with a supporting comparison of CUDA--SYCL performance retention on the evaluated NVIDIA platform. The latter uses the available median-time report and accounts for its configurations and the completeness of the underlying records.

\begin{researchquestion}[RQ3 -- Application transfer and CUDA--SYCL performance retention]
To what extent do the microbenchmarks and composite CG step predict communication costs and backend rankings in aCG, and which application dependencies explain agreement or divergence? For the SYCL version, how much native CUDA solver performance is retained on the evaluated platform?
\end{researchquestion}

\section{Scope and Main Findings}

The study uses 1 to 32 NVIDIA A100 GPUs on Leonardo's Booster partition. Isolated point-to-point, halo, reduction, and all-to-all tests compare seven CUDA- and SYCL-based stacks. A composite \texttt{cg\_step} benchmark adds a host-driven halo exchange and the small reductions characteristic of a CG iteration. The aCG campaign then evaluates complete host-initiated and monolithic device-initiated solvers on two large sparse matrices \cite{trotter_cpu-_2025}. The SYCL solver comparison uses a separate report for one matrix through 16 GPUs. All-to-all remains a standalone redistribution study.

The findings have three main implications for stack selection:
\begin{itemize}
\item \textbf{Rankings depend on the communication signature.} HPC-X MPI supplies the low-startup reference for point-to-point and isolated-halo communication, persistent device-initiated NVSHMEM leads large steady-state multi-node halos, and NCCL-based paths lead large allreduce and multi-node all-to-all. Runtime configuration can change these regimes substantially.
\item \textbf{Application prediction requires comparable primitives and dependencies.} The composite step predicts aCG's MPI and NCCL scalar-reduction costs closely, whereas its regular two-neighbor halo does not represent the solver's irregular exchange and overlap. The synthetic OSHMPI advantage does not establish a solver advantage: the application retains MPI scalar reductions and uses a blocking OSHMPI halo. The monolithic NVSHMEM solver scales better than that blocking path at larger process counts, but also reorganizes computation and synchronization.
\item \textbf{Solver implementation costs matter alongside communication.} The separate SYCL aCG report gives median solver times approximately 17--45\% higher than the CUDA reference at the reported GPU counts. These supporting report-level ratios do not isolate compiler or communication-library overhead; Chapter~\ref{ch:m-results} explains the remaining correctness-classification limitation.
\end{itemize}

Leonardo's NVSHMEM inter-node path uses a CPU proxy because InfiniBand GPUDirect Async (IBGDA) is unavailable \cite{trotter_cpu-_2025}. Thus the device-initiated cases evaluate kernel-side invocation with proxy-assisted networking. Chapter~\ref{ch:m-results} reports the quantitative boundaries and timing qualifications. It also presents a separate exploratory NCCL version and symmetric-buffer comparison, whose available summary does not establish application-visible device initiation.

\section{Major Contributions}

To answer these questions, this thesis makes five main contributions. The second and third extend oneCCL beyond the baseline backend behavior, while the fourth and fifth extend aCG beyond the published CUDA/HIP suite.

\begin{enumerate}

\item \textbf{A unified benchmark across vendor-specific and portable APIs.}
The harness applies common process-to-GPU mapping, warm-up, timing, validation, and result-reduction policies across seven MPI, NCCL/oneCCL, NVSHMEM, and OSHMPI stacks. Its primitive and composite patterns establish the comparison for RQ1 and RQ2 and the phase-level predictions tested by RQ3. The suite is available at \url{https://github.com/y3rbiadit0/gpu-comm-benchmark}.

\item \textbf{Grouped point-to-point support for the oneCCL NCCL backend.}
The extension propagates oneCCL's group lifecycle to NCCL, enabling mutually dependent send/receive batches used by halo and all-to-all exchanges. It preserves completion and error handling for deferred work and is covered by dedicated grouped point-to-point tests. This supplies a measured common-interface path for RQ2. The implementation is available at \url{https://github.com/y3rbiadit0/oneCCL/tree/fix/nccl_group_support}.

\item \textbf{SHMEM-family backend extensions for oneCCL.}
The complete OSHMPI backend implements collectives and point-to-point operations with symmetric staging for ordinary application buffers. Its measurements expose the cost of adapting oneCCL's event interface to blocking, host-driven OpenSHMEM operations. A separate NVSHMEM prototype establishes build integration, bootstrap, lifecycle, and symmetric staging, validated on one and two nodes. Its public collective entry points remain unsupported and provide no performance data. Together, these artifacts supply implementation and validation evidence for RQ2. They are available at \url{https://github.com/y3rbiadit0/oneCCL/tree/feat/oshmpi} and \url{https://github.com/y3rbiadit0/oneCCL/tree/feat/nvshmem_collectives}.

\item \textbf{An OSHMPI communicator and application validation in aCG.}
The communicator adds OpenSHMEM halo exchange while retaining CUDA-aware MPI scalar reductions. Evaluation against MPI, NCCL, host-NVSHMEM, and device-NVSHMEM solver variants on two SuiteSparse matrices connects the benchmark observations to overlap, synchronization, and convergence, supporting RQ2 and RQ3. The communicator is available at \url{https://github.com/y3rbiadit0/aCG-oshmpi/tree/oshmpi}.

\item \textbf{A SYCL implementation of aCG.}
The port provides distributed execution through MPI and selectable MPI or oneCCL scalar reductions. A separate solver-time comparison addresses RQ3's performance-retention question on the evaluated NVIDIA platform. The implementation is available at \url{https://github.com/y3rbiadit0/acg-sycl}.

\end{enumerate}
