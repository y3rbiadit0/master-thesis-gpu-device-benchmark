\chapter{Introduction}\label{ch}

Applications distributed across Graphics Processing Units (GPUs) must coordinate data movement as well as computation. When an application uses multiple GPUs within a node or across nodes, its communication stack determines how transfers are initiated, progressed, and completed, and how they interact with GPU kernels. Selecting a suitable stack therefore requires understanding both the application's communication needs and the execution costs of the available implementations.

This thesis investigates that selection problem through a progression from communication patterns to a complete application. A common benchmark identifies the regimes in which different stacks are effective; extensions to oneCCL (oneAPI Collective Communications Library) examine how additional communication paths can be exposed through a shared interface; and an extended Conjugate Gradient (CG) solver tests whether the benchmark guidance transfers to application execution. This chapter develops the motivation and research gaps behind that progression, defines the research questions, and summarizes the scope, findings, and contributions.

\section{Motivation}

GPUs provide the parallelism and memory bandwidth used by scientific simulations and large-scale artificial-intelligence workloads. Distributing these workloads introduces communication with different performance requirements: sparse solvers exchange boundary values and reduce scalar dot products, while distributed training combines gradients or redistributes activations. Scalability depends on the cost of these operations and on whether their dependencies leave communication exposed on the application's critical path \cite{unat_landscape_2026,choi_end--end_2020}.

Even when a transfer accesses GPU memory directly, the CPU may still issue the operation, wait for a producing kernel, and arrange completion before the next kernel starts. Repeated host orchestration can leave devices idle or prevent useful overlap. Moving communication calls into GPU kernels can reduce this overhead, but a host-driven library can remain efficient when its algorithms, batching, and progress mechanisms match the workload \cite{unat_landscape_2026,agostini_gpudirect_2018}.

Several programming models and libraries address these requirements. MPI (Message Passing Interface) provides a portable interface for distributed-memory point-to-point and collective communication. GPU-aware implementations accept device buffers, removing explicit host staging from application code and allowing direct GPU data movement. The implementation may still stage internally, depending on the operation, transport, and topology.

Vendor-optimized collective libraries, such as NVIDIA NCCL and AMD RCCL, provide specialized implementations of operations such as all-reduce, broadcast, reduce-scatter, and all-gather. These libraries are particularly important in distributed deep-learning workloads, where collective operations frequently dominate communication time \cite{weingram_xccl_2023}. Their performance depends on several internal decisions, including the selected communication algorithm, transport protocol, number of communication channels, and underlying system topology \cite{hu_demystifying_2025}.

A different approach is provided by one-sided Partitioned Global Address Space (PGAS) models such as OpenSHMEM. GPU-oriented implementations, including NVSHMEM and ROC\_SHMEM, extend this model by allowing communication operations to be initiated directly by GPU threads or thread blocks. Device-initiated communication can reduce CPU involvement and enable fine-grained communication from inside a kernel, potentially improving overlap and reducing synchronization overhead \cite{agostini_gpudirect_2018,ma_demystifying_2026}. Portable implementations such as OSHMPI instead provide OpenSHMEM semantics over MPI. These alternatives make different trade-offs: symmetric-memory requirements, synchronization semantics, message granularity, host involvement, and implementation maturity can all determine whether one-sided communication is beneficial.

These alternatives create a practical selection problem. The relevant input is the application's \emph{communication signature}: its operations, message sizes, peer sets, synchronization points, rank placement, and opportunities for computation--communication overlap. Recent studies show that default collective configurations can be substantially slower than choices made for a particular topology and workload \cite{pasqualoni_pico_2026,li_tuccl_2025}. Both the backend and its configuration therefore belong in the selection process.

Vendor-specific ecosystems generally provide highly optimized implementations, but they couple applications to a particular hardware and software stack. SYCL and oneCCL provide source-level abstractions that reduce this coupling. Source portability, runtime backend interchangeability, and performance portability are nevertheless distinct properties: a common interface may add orchestration, staging, or synchronization costs, and measurements on NVIDIA A100 GPUs cannot by themselves establish cross-vendor performance portability \cite{hammond_comparative_2019,shen_sycl_2026}. This thesis therefore treats CUDA and SYCL variants as concrete implementation stacks and supporting controls, rather than making cross-vendor portability a separate experimental claim.

\subsection{Research Gap}

Prior work already connects communication mechanisms to applications. GPUDirect Async has been examined through microbenchmarks, modeling, and application cases \cite{agostini_gpudirect_2018}; PICO assesses benchmark-informed choices through simulated training-trace replay \cite{pasqualoni_pico_2026}; TuCCL reports end-to-end training improvements \cite{li_tuccl_2025}; and host- and device-initiated CG solvers have been compared directly \cite{trotter_cpu-_2025}. Building on these studies, this thesis investigates three connected questions left open for the selected stacks and application:

\begin{itemize}
\item \emph{Comparable characterization across communication stacks.}
Separate library benchmarks do not establish how the selected MPI, collective-library, and SHMEM paths rank under a shared measurement policy. A common CUDA/SYCL harness makes it possible to locate favorable performance regimes while recording the memory, completion, and progress differences that qualify the comparison.

\item \emph{Performance and integration costs of SHMEM-style communication.}
Direct SHMEM measurements do not establish how much performance survives the buffer and completion adaptations required by a common interface. Comparing NVSHMEM and OSHMPI with MPI and NCCL exposes their direct trade-offs; implementing the missing paths in the oneCCL source used for this work exposes the integration requirements. Grouped NCCL support and an OSHMPI backend covering the benchmarked world-communicator operation set provide executable comparison paths, while a separately validated NVSHMEM runtime foundation establishes the prerequisites for a further backend.

\item \emph{Transfer from communication patterns to solver execution.}
It remains to be established which observations from this comparison predict application performance once irregular peers, computation, and convergence are included. Extending the published CUDA/HIP aCG suite with an OSHMPI communicator enables that test for an additional one-sided halo path. A SYCL implementation supports a subsidiary investigation of how much native CUDA solver performance a portable implementation retains on the same platform.
\end{itemize}

\begin{keypoint}[Central proposition]
Persistent device work can amortize host-control costs, but memory placement, completion semantics, and progress determine the favorable regimes. Pattern-oriented measurements can guide backend selection when the application's peer structure and dependencies preserve those regimes.
\end{keypoint}

The benchmark consequently covers reductions, neighbor exchanges, and all-to-all redistribution, with point-to-point tests as a transfer reference. Iterative sparse solvers motivate small reductions and halo exchanges; distributed training on rapidly growing AI supercomputers \cite{pilz_trends_2025} motivates bulk reductions; and Mixture-of-Experts (MoE) models, which route each token to a small number of expert submodels held on different devices \cite{mu_comprehensive_2026}, motivate uniform and variable-count redistribution. The application study validates the reduction and halo families through aCG.

\section{Research Questions}

Selecting a communication stack begins with a practical uncertainty: when does moving communication calls into a GPU kernel repay the cost of changing the execution path? A host-driven application may repeatedly wait for a producing kernel, submit a transfer, and establish completion before computation can continue. Persistent device execution offers a way to keep this sequence on the GPU, but introduces its own synchronization and progress requirements. The first step is therefore to locate the message sizes and topologies at which the balance changes. The persistent NVSHMEM ping-pong and halo kernels provide this evidence at pattern level, while the monolithic NVSHMEM solver extends the investigation to repeated application execution. Because these paths also differ in algorithms and organization, the comparison concerns the benefit of each complete stack.

\begin{researchquestion}[RQ1 -- Conditions for beneficial GPU initiation]
Under which evaluated configurations do persistent NVSHMEM ping-pong and halo kernels and the monolithic NVSHMEM aCG solver outperform host-initiated alternatives? What evidence supports launch, synchronization, or proxy-progress costs as explanations for the observed message-size and scaling boundaries?
\end{researchquestion}

A favorable timing is only the beginning of an adoption decision. To use a SHMEM path, an application must establish suitable memory, identify remote destinations, and coordinate completion and buffer reuse. NVSHMEM and OSHMPI expose these responsibilities through different execution and progress mechanisms. Adopting them beneath oneCCL adds another requirement: the adapter must reconcile those mechanisms with ordinary application buffers and an event-based interface. Staging or blocking synchronization may consume part of the advantage observed in a direct benchmark. The second question consequently asks what the measured performance requires from the programmer and runtime, and how those requirements change when communication is exposed through a common interface.

\begin{researchquestion}[RQ2 -- Practical trade-offs of SHMEM-style communication]
How do the evaluated NVSHMEM and OSHMPI paths compare with MPI and NCCL in performance and programming requirements? What memory, ordering, completion, and progress adaptations are required beneath oneCCL, and what costs are measured for the completed adapters?
\end{researchquestion}

The next step is to put the candidate paths back into an application. In a CG solver, halo data arrives from an irregular set of peers, local matrix--vector work may hide part of the transfer, and small global reductions can delay the next update. A path that wins an isolated exchange may therefore contribute little to solver performance, while a modest reduction-latency improvement may matter on every iteration. Moving from individual patterns through the composite CG step to complete aCG execution tests which benchmark observations remain useful once these dependencies and convergence are included.

The application also makes the portability question concrete. Expressing the solver through SYCL changes kernels, memory handling, and host orchestration alongside the available communication interfaces. The final question therefore combines the main test of benchmark-to-application transfer with a supporting comparison of CUDA--SYCL performance retention on the evaluated NVIDIA platform. The latter uses the available median-time report and accounts for its configurations and the completeness of the underlying records.

\begin{researchquestion}[RQ3 -- Application transfer and CUDA--SYCL performance retention]
To what extent do the microbenchmarks and composite CG step predict communication costs and backend rankings in aCG, and which application dependencies explain agreement or divergence? For the SYCL version, how much native CUDA solver performance is retained on the evaluated platform?
\end{researchquestion}

\section{Scope and Findings}

The study uses 1 to 32 NVIDIA A100 GPUs on Leonardo's Booster partition. Isolated point-to-point, halo, reduction, and all-to-all tests cover a union of seven CUDA- and SYCL-based stacks; exact backend availability differs by pattern. Two application microbenchmarks follow: \texttt{moe} reproduces the dispatch and combine of an MoE layer, replacing the equal-block assumption of all-to-all with routing-dependent, variable-count exchanges, and a composite \texttt{cg\_step} benchmark adds a host-driven halo exchange and the small reductions characteristic of a CG iteration. The aCG campaign then evaluates complete host-initiated and monolithic device-initiated solvers on two large sparse matrices \cite{trotter_cpu-_2025}. The SYCL solver comparison uses a separate report for one matrix through 16 GPUs. Redistribution is validated at the microbenchmark level only; no complete application exercises it here.

The findings have three main implications for stack selection, reported in full in Chapter~\ref{ch:m-results} and synthesized in Chapter~\ref{ch:m-discussion}:
\begin{itemize}
\item \emph{Rankings depend on the communication signature.} No stack leads everywhere. MPI supplies the low-startup reference, persistent device-initiated NVSHMEM leads large batched multi-node halos, and NCCL-based paths lead bulk collectives. Runtime configuration can move these boundaries as much as the library choice does, and so can the payload distribution: holding operation, topology, and total volume fixed, the MoE benchmark reverses the bulk redistribution ranking.
\item \emph{Cross-level agreement requires comparable primitives and dependencies.} Scalar reduction costs measured in the composite step agree closely with the solver, whereas its regular two-neighbor halo does not represent the solver's irregular exchange and overlap. A benchmark predicts an application only where the operation, its completion contract, and its dependencies match.
\item \emph{Implementation costs matter alongside communication.} Expressing communication through SYCL rather than CUDA costs about one percent in the communication-only patterns, but the complete SYCL solver is measurably slower, so the gap belongs to kernels and host orchestration rather than to the communication path.
\end{itemize}

The distinction between intra- and inter-node communication is central to this characterization. For NVSHMEM's device-side one-sided transfers, the evaluated platform provides two execution paths. Within a node, the peer's symmetric heap is directly mapped into the local GPU's address space, allowing GPU threads to move data through loads and stores over NVLink: the \emph{fast path}. Across nodes, the peer heap cannot be accessed through such a mapping, so operations use a network transport: the \emph{slow path}. On supported systems, InfiniBand GPUDirect Async (IBGDA) allows GPU code to construct and post network work requests directly to the InfiniBand adapter. Otherwise, the GPU writes a request descriptor into pinned host memory, and a dedicated CPU proxy thread consumes it and submits the network operation. Both alternatives belong to the network slow path \cite{ma_demystifying_2026}.

IBGDA can reduce the latency of this network path by removing the GPU-to-CPU request hand-off and CPU-proxy servicing, making it particularly relevant to small, frequent transfers and strongly scaled workloads \cite{ma_demystifying_2026}. Under the evaluated transport configuration (Section~\ref{sec:ibgda-check}), the topology sweep characterizes NVSHMEM's mapped-memory intra-node regime, its proxy-assisted inter-node regime, and their combination in multi-node, multi-GPU execution. This establishes where the evaluated stacks retain or lose their advantages when communication crosses the network (Section~\ref{sec:micro-scaling}); the additional benefit of IBGDA would require a matched measurement with that path enabled.

Chapter~\ref{ch:m-results} reports the quantitative boundaries and timing qualifications. A separate exploratory NCCL version and symmetric-buffer comparison is retained in Appendix~\ref{app:nccl-preliminary}; its available summary does not establish application-visible device initiation and contributes no evidence to the research-question answers.

\section{Contributions}

To answer these questions, this thesis makes five main contributions. The second and third extend oneCCL beyond the baseline backend behavior, while the fourth and fifth extend aCG beyond the published CUDA/HIP suite.

\begin{enumerate}

\item \emph{A unified benchmark across vendor-specific and portable APIs.}
The harness applies common process-to-GPU mapping, warm-up, timing, validation, and result-reduction policies across seven MPI, NCCL/oneCCL, NVSHMEM, and OSHMPI stacks. Its primitive and composite patterns establish the comparison for RQ1 and RQ2 and the phase-level cross-context checks used by RQ3. The suite is available in \cite{merenda_gpu_comm_benchmark_2026}.

\item \emph{Grouped point-to-point support for the oneCCL NCCL backend.}
The extension propagates oneCCL's group lifecycle to NCCL, enabling mutually dependent send/receive batches used by halo and all-to-all exchanges. It preserves completion and error handling for deferred work and is covered by dedicated grouped point-to-point tests. This supplies a measured common-interface path for RQ2. The implementation is available in \cite{merenda_oneccl_nccl_groups_2026}.

\item \emph{SHMEM-family backend extensions for oneCCL.}
The OSHMPI backend implements the benchmarked world-communicator collectives and point-to-point operations with symmetric staging for ordinary application buffers. Its measurements expose the cost of adapting oneCCL's event interface to blocking, host-driven OpenSHMEM operations. A separate NVSHMEM prototype establishes build integration, bootstrap, lifecycle, and symmetric staging, validated on one and two nodes. Its public collective entry points remain unsupported and provide no performance data. Together, these artifacts supply implementation and validation evidence for RQ2. They are available in \cite{merenda_oneccl_oshmpi_2026,merenda_oneccl_nvshmem_2026}.

\item \emph{An OSHMPI communicator and application validation in aCG.}
The communicator adds OpenSHMEM halo exchange while retaining CUDA-aware MPI scalar reductions. Evaluation against MPI, NCCL, host-NVSHMEM, and device-NVSHMEM solver variants on two SuiteSparse matrices connects the benchmark observations to overlap, synchronization, and convergence, supporting RQ2 and RQ3. The communicator is available in \cite{merenda_acg_oshmpi_2026}.

\item \emph{A SYCL implementation of aCG.}
The port provides distributed execution through MPI and selectable MPI or oneCCL scalar reductions. A separate solver-time comparison addresses RQ3's performance-retention question on the evaluated NVIDIA platform. The implementation is available in \cite{merenda_acg_sycl_2026}.

\end{enumerate}
