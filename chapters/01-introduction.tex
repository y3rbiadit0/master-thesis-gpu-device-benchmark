\chapter{Introduction}\label{ch}

Applications distributed across \acp{GPU} must coordinate data movement as well as computation. When an application uses multiple GPUs within a node or across nodes, its communication stack determines who starts each transfer, how it proceeds, and when the next computation can use the result. Selecting a suitable stack requires understanding both the application's communication needs and the costs of meeting them.

This thesis asks when initiating communication on the GPU improves performance and whether benchmarks can help developers choose a stack for their application. The evaluation proceeds in three steps. A common benchmark compares stacks across message sizes and node layouts. Extensions to the \ac{oneCCL} measure the cost of using these libraries through a shared interface. An extended \ac{CG} solver then tests whether the benchmark results remain useful once communication is combined with computation. This chapter develops the motivation and research gaps, defines the \acp{RQ}, and summarizes the scope, results, and contributions.

\section{Motivation}

GPUs provide the parallelism and memory bandwidth used by scientific simulations and large-scale \ac{AI} workloads. This thesis focuses on two application classes to motivate its benchmark patterns: iterative sparse solvers and distributed training. Together, they expose contrasting communication requirements, from small, synchronization-sensitive exchanges to bulk collective data movement. Sparse solvers exchange boundary values and reduce scalar dot products, while distributed training combines gradients or redistributes activations. Scalability depends on the cost of these operations and on whether their dependencies leave communication exposed on the application's critical path \cite{unat_landscape_2026,choi_end--end_2020}.

Even when a transfer accesses GPU memory directly, the \ac{CPU} may still issue the operation, wait for a producing kernel, and arrange completion before the next kernel starts. Repeated host orchestration can leave devices idle or prevent useful overlap. Moving communication calls into GPU kernels can reduce this overhead, but a host-driven library can remain efficient when its algorithms, batching, and progress mechanisms match the workload \cite{unat_landscape_2026,agostini_gpudirect_2018}.

Several programming models and libraries address these requirements. The \ac{MPI} provides a portable interface for distributed-memory point-to-point and collective communication. GPU-aware MPI implementations extend this support to GPU-resident data by accepting device buffers directly, removing explicit host staging from application code and allowing direct GPU data movement. The implementation may still stage internally, depending on the operation, transport, and topology.

Vendor-optimized collective libraries, such as the \ac{NCCL} and AMD's \ac{RCCL}, provide specialized implementations of operations such as all-reduce, broadcast, reduce-scatter, and all-gather. These libraries are particularly important in distributed deep-learning workloads, where collective operations frequently dominate communication time \cite{weingram_xccl_2023}. Their performance depends on several internal decisions, including the selected communication algorithm, transport protocol, number of communication channels, and underlying system topology \cite{hu_demystifying_2025}.

A different approach is provided by one-sided \ac{PGAS} models such as OpenSHMEM, an open specification of the \ac{SHMEM} programming model. GPU-oriented implementations, including the \ac{NVSHMEM} and ROC\_SHMEM, extend this model by allowing communication operations to be initiated directly by GPU threads or thread blocks. Device-initiated communication can reduce CPU involvement and enable fine-grained communication from inside a kernel, potentially improving overlap and reducing synchronization overhead \cite{agostini_gpudirect_2018,ma_demystifying_2026}. Portable implementations such as \ac{OSHMPI} implement the OpenSHMEM programming model using MPI as the underlying communication layer. These alternatives make different trade-offs: symmetric-memory requirements, synchronization semantics, message granularity, host involvement, and implementation maturity can all determine whether one-sided communication is beneficial.

These alternatives create a practical selection problem. Choosing a suitable stack requires understanding the application's \emph{communication signature}: its operations, message sizes, peer sets, synchronization points, rank placement, and opportunities for computation--communication overlap. Recent studies show that default collective configurations can be substantially slower than choices made for a particular topology and workload \cite{pasqualoni_pico_2026,li_tuccl_2025}. Both the backend and its configuration therefore belong in the selection process.

Vendor-specific ecosystems generally provide highly optimized implementations, but they couple applications to a particular hardware and software stack. SYCL and oneCCL can make it easier to reuse application code across different hardware and communication libraries. However, changing the library behind a common interface may introduce extra buffer copies or waits between computation and communication. Code that runs on different systems may also perform well on some and poorly on others \cite{hammond_comparative_2019,shen_sycl_2026}. This thesis compares \ac{CUDA} and SYCL implementations on NVIDIA A100 GPUs to measure these costs on one platform; it does not evaluate performance across vendors.

\subsection{Research Gap}

Prior work already connects communication mechanisms to applications. GPUDirect Async has been examined through microbenchmarks, modeling, and application cases \cite{agostini_gpudirect_2018}; PICO assesses benchmark-informed choices through simulated training-trace replay \cite{pasqualoni_pico_2026}; TuCCL reports end-to-end training improvements \cite{li_tuccl_2025}; and host- and device-initiated CG solvers have been compared directly \cite{trotter_cpu-_2025}. Building on these studies, this thesis investigates three connected questions left open for the selected stacks and application:

\begin{itemize}
\item \emph{Comparable characterization across communication stacks.}

Separate library benchmarks use different timing and execution rules, making their results difficult to compare directly. A common CUDA/SYCL benchmark framework can identify which selected MPI, collective-library, and SHMEM implementations perform well at each message size and topology. It must also record where data is stored, how transfers progress, and when each operation is considered complete, because those differences affect the comparison.

\item \emph{Performance and integration costs of SHMEM-style communication.}
A communication library may perform well when used directly but lose some of that advantage when accessed through a common interface such as oneCCL. The interface may require extra buffer copies or waits for communication to finish. This thesis first compares NVSHMEM and OSHMPI directly with MPI and NCCL. It then adds grouped NCCL support and an OSHMPI backend to oneCCL to examine the implementation effort and measure the overhead of using these paths through a shared interface.

\item \emph{Transfer from communication patterns to solver execution.}
The next question is which benchmark results help predict application performance once irregular peers, computation, and convergence are included. Extending the published \ac{aCG} suite, which provides CUDA and \ac{HIP} implementations, with an OSHMPI communicator allows this test for another one-sided halo implementation. A SYCL implementation also tests how much native CUDA solver performance a portable implementation retains on the same platform.
\end{itemize}

\begin{keypoint}[Central proposition]

One motivation for GPU-initiated communication is to reduce the CPU's role in coordinating computation and data transfers. A persistent kernel takes this further by keeping work running on the GPU instead of repeatedly returning control to the CPU. This can reduce coordination overhead, but whether the application runs faster depends on the problem: how much computation it performs, what data it exchanges, and how often it must wait for communication. Benchmarks that reflect these characteristics can help identify when persistent GPU execution is useful and which communication stack best suits the application.

\end{keypoint}

The benchmark consequently covers reductions, neighbor exchanges, and all-to-all redistribution, with point-to-point tests as a transfer reference. Iterative sparse solvers motivate small reductions and halo exchanges; distributed training on rapidly growing AI supercomputers \cite{pilz_trends_2025} motivates bulk reductions; and \ac{MoE} models, which route each token to a small number of expert submodels held on different devices \cite{mu_comprehensive_2026}, motivate uniform and variable-count redistribution. The application study validates the reduction and halo families through aCG.

\section{Research Questions}

Selecting a communication stack begins with a practical uncertainty: when does moving communication calls into a GPU kernel repay the cost of changing the execution path? A host-driven application may repeatedly wait for a producing kernel, submit a transfer, and establish completion before computation can continue. Persistent device execution offers a way to keep this sequence on the GPU, but introduces its own synchronization and progress requirements. The first step is therefore to locate the message sizes and topologies at which the balance changes. The persistent NVSHMEM ping-pong and halo kernels provide this evidence at pattern level, while the monolithic NVSHMEM solver extends the investigation to repeated application execution. Because these paths also differ in algorithms and organization, the comparison concerns the benefit of each complete stack.

\begin{researchquestion}[RQ1 -- When GPU initiation pays off]
Under which evaluated configurations do persistent NVSHMEM ping-pong and halo kernels and the monolithic NVSHMEM aCG solver outperform host-initiated alternatives? What evidence helps explain these results in terms of kernel-launch overhead, synchronization delays, or the overhead of a CPU proxy thread handling GPU communication requests?
\end{researchquestion}

Benchmark performance alone is not enough to decide whether to use a communication library. Using SHMEM also requires allocating memory that other processes can access, identifying where to send data, and ensuring transfers finish before buffers are reused. NVSHMEM and OSHMPI differ in how communication is started and carried out. Integrating a SHMEM library into oneCCL requires additional work to accept application buffers and provide events that indicate when operations have finished. Extra buffer copies or waits may reduce the performance benefit measured when using the library directly. The second question therefore examines both the effort required to use these libraries and the overhead introduced by a common interface.

\begin{researchquestion}[RQ2 -- Practical trade-offs of SHMEM-style communication]
How do the evaluated NVSHMEM and OSHMPI paths compare with MPI and NCCL in performance and programming requirements? What memory, ordering, completion, and progress adaptations are required beneath oneCCL, and what costs are measured for the completed adapters?
\end{researchquestion}

The next step is to put the candidate stacks into an application. In a CG solver, halo data arrives from an irregular set of peers, local matrix--vector work may hide part of the transfer, and small global reductions can delay the next update. A stack that wins an isolated exchange may contribute little to solver performance, while a modest reduction-latency improvement may matter on every iteration. Moving from individual patterns through a simplified CG iteration benchmark, \texttt{cg\_step}, to aCG tests which benchmark observations remain useful once these dependencies and convergence are included.

The application also makes the portability question concrete. Expressing the solver through SYCL changes kernels, memory handling, and host orchestration alongside the available communication interfaces. The final question therefore combines the main test of benchmark-to-application transfer with a supporting comparison of CUDA--SYCL performance retention on the evaluated NVIDIA platform. The latter pairs a SYCL solver campaign with the CUDA solver on the same problems and partitions.

\begin{researchquestion}[RQ3 -- From benchmarks to applications, and SYCL performance retention]
To what extent do the microbenchmarks and the \texttt{cg\_step} benchmark predict communication costs and backend rankings in aCG, and which application dependencies explain agreement or divergence? For the SYCL version, how much native CUDA solver performance is retained on the evaluated platform?
\end{researchquestion}

\section{Scope and Findings}

Isolated point-to-point, halo, reduction, and all-to-all tests cover a union of seven CUDA- and SYCL-based stacks; exact backend availability differs by pattern. Two application microbenchmarks follow: \texttt{moe} reproduces the dispatch and combine of an MoE layer, replacing the equal-block assumption of all-to-all with routing-dependent, variable-count exchanges, and the \texttt{cg\_step} benchmark combines a halo exchange, local stencil computation, and two scalar reductions to represent part of a CG iteration. It omits vector updates and convergence checks, so it measures a simplified sequence rather than a complete solver iteration. The aCG campaign then evaluates complete host-initiated and monolithic device-initiated solvers on two large sparse matrices \cite{trotter_cpu-_2025}. A separate paired campaign compares the SYCL and native CUDA solvers on both matrices, running both implementations in the same allocations. Redistribution is validated at the microbenchmark level only; no complete application exercises it here. These experiments use 1 to 32 NVIDIA A100 GPUs on Leonardo's Booster partition.

The findings have three main implications for stack selection, reported in full in Chapter~\ref{ch:m-results} and synthesized in Chapter~\ref{ch:m-discussion}:
\begin{itemize}
\item \emph{Rankings depend on the communication signature.} No stack leads everywhere. MPI supplies the low-startup reference, persistent device-initiated NVSHMEM leads large batched multi-node halos, and NCCL-based paths lead bulk collectives. Runtime configuration can move these boundaries as much as the library choice does, and so can the payload distribution: holding operation, topology, and total volume fixed, the MoE benchmark reverses the bulk redistribution ranking.
\item \emph{Agreement between benchmark and solver requires comparable operations and dependencies.} Scalar reduction costs measured in the \texttt{cg\_step} benchmark agree closely with the solver, whereas its regular two-neighbor halo does not represent the solver's irregular exchange and overlap. The benchmark results agree with the application where the operations, completion requirements, and dependencies match.
\item \emph{Implementation costs matter alongside communication.} Expressing communication through SYCL rather than CUDA costs about one percent in the communication-only patterns. The SYCL solver keeps the native data layout and synchronization structure and matches the native one within a node. Across nodes, the oneCCL adapter introduces host waits for reductions, showing why synchronization choices matter when assessing portability costs.
\end{itemize}

The distinction between intra- and inter-node communication is central to this characterization. For NVSHMEM's device-side one-sided transfers, the evaluated platform provides two execution paths. Within a node, the peer's symmetric heap is directly mapped into the local GPU's address space, allowing GPU threads to move data through loads and stores over NVLink: the \emph{fast path}. Across nodes, the peer heap cannot be accessed through such a mapping, so operations use a network transport: the \emph{slow path}. On supported systems, \ac{IBGDA} allows GPU code to construct and post network work requests directly to the InfiniBand adapter. Otherwise, the GPU writes a request descriptor into pinned host memory, and a dedicated CPU proxy thread consumes it and submits the network operation. Both alternatives belong to the network slow path \cite{ma_demystifying_2026}.

IBGDA can reduce network latency by removing the GPU-to-CPU request hand-off and CPU-proxy servicing, making it particularly relevant to small, frequent transfers and strongly scaled workloads \cite{ma_demystifying_2026}. Under the evaluated transport configuration (Section~\ref{sec:ibgda-check}), the topology sweep tests NVSHMEM's mapped-memory transfers within a node, its proxy-assisted transfers across nodes, and their combination in multi-node, multi-GPU execution. This shows where the evaluated stacks retain or lose their advantages when communication crosses the network (Section~\ref{sec:micro-scaling}). Measuring the additional benefit of IBGDA would require a matched experiment with that transport enabled.

Chapter~\ref{ch:m-results} reports the measured performance and explains how to interpret each timing. Appendix~\ref{app:nccl-preliminary} presents a separate exploratory comparison of NCCL versions and symmetric buffers. Its summary does not identify whether application kernels initiated communication, so it is excluded from the research-question answers.

\section{Contributions}

To answer these questions, this thesis makes five main contributions. The second and third extend oneCCL beyond the baseline backend behavior, while the fourth and fifth extend aCG beyond the published CUDA/HIP suite.

\begin{enumerate}

\item \emph{A unified benchmark across vendor-specific and portable \acp{API}.}
The benchmark suite compares seven communication stacks based on MPI, NCCL/oneCCL, NVSHMEM, and OSHMPI. It uses consistent procedures to assign processes to GPUs, warm up each test, measure execution time, check correctness, and summarize results. Its individual communication tests and application microbenchmarks support RQ1 and RQ2. Comparing these measurements with the corresponding communication phases in aCG supports RQ3. The suite is available in \cite{merenda_gpu_comm_benchmark_2026}.

\item \emph{Grouped point-to-point support for the oneCCL NCCL backend.}
The extension propagates oneCCL's group lifecycle to NCCL, enabling mutually dependent send/receive batches used by halo and all-to-all exchanges. It preserves completion and error handling for deferred work and is covered by dedicated grouped point-to-point tests. This supplies a measured common-interface path for RQ2. The implementation is available in \cite{merenda_oneccl_nccl_groups_2026}.

\item \emph{SHMEM-family backend extensions for oneCCL.}
The OSHMPI backend implements the benchmarked world-communicator collectives and point-to-point operations with symmetric staging for ordinary application buffers. Its measurements expose the cost of adapting oneCCL's event interface to blocking, host-driven OpenSHMEM operations. A separate NVSHMEM prototype establishes build integration, bootstrap, lifecycle, and symmetric staging, validated on one and two nodes. Its public collective entry points remain unsupported and provide no performance data. Together, these artifacts supply implementation and validation evidence for RQ2. They are available in \cite{merenda_oneccl_oshmpi_2026,merenda_oneccl_nvshmem_2026}.

\item \emph{An OSHMPI communicator and application validation in aCG.}
The communicator adds OpenSHMEM halo exchange while retaining CUDA-aware MPI scalar reductions. Evaluation against MPI, NCCL, host-NVSHMEM, and device-NVSHMEM solver variants on two SuiteSparse matrices connects the benchmark observations to overlap, synchronization, and convergence, supporting RQ2 and RQ3. The communicator is available in \cite{merenda_acg_oshmpi_2026}.

\item \emph{A SYCL implementation of aCG.}
The port provides distributed execution through MPI and selectable MPI or oneCCL scalar reductions. A separate solver-time comparison addresses RQ3's performance-retention question on the evaluated NVIDIA platform. The implementation is available in \cite{merenda_acg_sycl_2026}.

\end{enumerate}
