\chapter{Experimental Methodology}\label{ch:m-methodology}

This chapter defines the experiment behind the comparison of host-driven and device-initiated communication on a GPU-accelerated cluster. It sets out the measurement design and its parameters, the platform and the configured stacks that are actually compared, the timing and statistical protocol, the communication patterns and the application validation built on them, and the boundaries of what the retained evidence supports. The recurring concern is attribution: the evaluated paths differ in compute interface, memory handling, completion semantics, and transport as well as in where communication is invoked, so the design states throughout which of those differences a given comparison holds fixed and which it does not.

\section{Research Planning}\label{sec:research-planning-levels}

The evaluation employs a bottom-up approach, progressing from isolated microbenchmarks to a full application context. This progression is structured in three levels, and the campaign was executed in that order, because each level uses the preceding one to choose what is worth measuring:

\begin{enumerate}
    \item \textbf{Isolated communication microbenchmarks:} \texttt{pingpong}, \texttt{halo\_1d}, \texttt{allreduce}, and \texttt{alltoall} exercise one operation at a time, with no computation to overlap or distort the transfer. They establish the message sizes, topologies, and runtime settings at which a given backend is competitive.
    \item \textbf{Application microbenchmarks:} \texttt{moe} and \texttt{cg\_step} retain the same harness, timing contract, and validation policy, but replace a single operation with a workload's communication sequence. \texttt{moe} adds routing-dependent, variable-count redistribution; \texttt{cg\_step} combines a halo exchange, a local stencil, and two scalar reductions. They test whether the isolated observations survive composition, either with an irregular payload distribution or with local computation.
    \item \textbf{Full \texttt{aCG} solver:} Tests cross-level agreement by introducing sparse partitioning, realistic application dependencies, and convergence criteria.
\end{enumerate}

Of the two application microbenchmarks, \texttt{cg\_step} is the one carried into the cross-level comparison of Section~\ref{sec:acg-method}, because the solver evaluated in this thesis is a CG solver and its reductions can be matched by datatype and payload. \texttt{moe} has no matched application in this campaign; it is measured to test how strongly the ranking obtained from a uniform, fixed-count exchange depends on the payload distribution assumed by that exchange.

Raising the application context in steps is what makes the levels diagnostic: each one adds a single class of application property, so a ranking that changes between two levels identifies which property caused it.

The unit of comparison is a configured runtime stack, not a library. Each stack fixes a compute interface, a communication path, and a completion contract together, and the evaluated device-initiated paths differ from their host-driven counterparts in all three, not only in where a transfer is invoked. The design therefore aims to locate performance regimes rather than to attribute differences to invocation alone; Section~\ref{sec:eval-environment} describes the environment and the seven stacks, including the differences each comparison leaves uncontrolled.

A \emph{cell} is one $(\text{pattern}, \text{stack}, \text{topology})$ combination, swept over the payload axis. Topology is given as $N$ nodes by $G$ GPUs rather than as a rank count, because equal rank counts can use different interconnects; \texttt{1n4g} and \texttt{2n1g} are both measured for that reason. Each pattern has a fixed collective policy, such as whether UCC is enabled, described in Section~\ref{sec:runtime-method}.

\paragraph{Timing.} Each trial first runs untimed warm-up iterations, which absorb one-time costs such as buffer registration, connection establishment, and algorithm selection, and then its timed iterations. A timed iteration covers the complete operation from submission to observed completion; setup and correctness checks are excluded (Section~\ref{sec:completion-method}). The timed iterations of a trial form one sample series and are not treated as independent repetitions.

\paragraph{Independence.} Every cell was run as five independent repetitions. Each repetition is a separate scheduler job that obtains its own allocation, so repetitions share no process state and may differ in nodes and network routes. Within one allocation the benchmark is launched three times. Only allocations are treated as independent samples: trial means are averaged within each allocation, the reported value is the median of the allocation means, and shaded bands show their minimum--maximum range, which describes observed variation rather than a confidence interval.

\paragraph{Exceptions to the defaults.} The retained all-to-all and \texttt{cg\_step} sweeps contain three allocations instead of five, each still with three trials; their counts are reported as measured and not reweighted. \texttt{cg\_step} also uses 50 timed and 10 warm-up iterations instead of 100 and 20.

\subsection{Benchmark Tooling}\label{sec:harness}

The campaign was run with the command-line tooling of the benchmark suite contributed by this thesis (Chapter~\ref{ch}), available at \url{https://github.com/y3rbiadit0/gpu-comm-benchmark}. It covers the workflow from an empty checkout to recorded results, so that every stack is built, launched, and logged in the same way:

\begin{itemize}
    \item \textbf{Initialization.} One command bootstraps the source-built dependencies, including OSHMPI and the two oneCCL backends, in dependency order, and builds all seven stacks from shared build presets. Libraries provided by the site, such as HPC-X MPI, are taken from the system modules.
    \item \textbf{Execution.} Experiments can be submitted for a single cell, for one pattern, or for the complete declared matrix of patterns, stacks, and topologies. Iteration counts, trials, and collective policy are defined once per pattern and apply to every stack, and the resolved configuration of a cell can be inspected before submission.
    \item \textbf{Library versions.} NCCL and NVSHMEM releases are selected with a single variable that gives each version its own installation, build, and results directory, so measurements of different versions cannot be mixed. Source-built dependencies are pinned to a revision and rebuilt when changed.
    \item \textbf{Recording.} Each trial log records the job, nodes, stack, launcher, and communication-relevant environment. Output is kept as a result only if the trial completes successfully within its timeout; failed runs are retained separately for inspection.
    \item \textbf{Portability.} Machine-specific modules and transport settings are kept apart from the experiment definitions, so the same experiments can target another cluster by adding a cluster definition.
\end{itemize}

\section{Experimental Setup}\label{sec:eval-environment}

All experiments were run on the Booster partition of the Leonardo supercomputer at CINECA \cite{turisini_leonardo_2024}, ranked 12th in the June 2026 TOP500 list \cite{top500_june2026}. Intra-node experiments use a single node with one, two, or four GPUs; multi-node experiments use two, four, or eight nodes of the same partition, up to 32 GPUs. One process drives one GPU throughout. This section describes the node hardware, the communication paths it provides, the software environment, and the stacks built on it.

\subsection{Booster Node Specifications}

\begin{itemize}
    \item \textbf{Model:} Atos BullSequana X2135 ``Da Vinci'' single-node GPU blade.
    \item \textbf{Processor:} one Intel Xeon Platinum 8358 (Ice Lake), 32 cores at 2.60\,GHz.
    \item \textbf{GPU:} four NVIDIA A100 SXM4 GPUs with 64\,GB of HBM2e each.
    \item \textbf{Memory:} 512\,GB DDR4 at 3200\,MHz ($8 \times 64$\,GB).
    \item \textbf{Intra-node interconnect:} NVLink~3.0, with each GPU connected directly to the other three by four links, giving 200\,GB/s of bidirectional bandwidth per GPU pair; there is no NVSwitch.
    \item \textbf{Network:} NVIDIA Mellanox InfiniBand HDR in a DragonFly+ topology, with two dual-port HDR100 adapters per node, exposed as four 100\,Gb/s interfaces.
    \item \textbf{Scheduler:} Slurm.
\end{itemize}

\subsection{Intra- and Inter-Node Communication Support}

The node provides two communication domains with an order-of-magnitude difference in bandwidth, and the topology set is chosen to observe each separately and in combination:

\begin{enumerate}
    \item \textbf{Intra-node communication} between GPUs of the same node travels over the direct NVLink connections, using GPUDirect peer-to-peer access without staging through host memory. A single GPU pair has a 100\,GB/s ceiling per direction. The \texttt{1n2g} and \texttt{1n4g} topologies use only this domain, and \texttt{1n1g} serves as a single-GPU control with no inter-rank transfer.
    \item \textbf{Inter-node communication} between nodes travels over InfiniBand, where GPUDirect RDMA lets the adapter read and write registered GPU memory directly. One HDR100 port carries 100\,Gb/s, or 12.5\,GB/s. The \texttt{2n1g} topology isolates this domain with one GPU per node, while \texttt{2n4g}, \texttt{4n4g}, and \texttt{8n4g} combine both domains at 8, 16, and 32 GPUs.
\end{enumerate}

Comparing \texttt{1n4g} with \texttt{2n1g} therefore separates a change of interconnect from a change of scale, which a rank-count axis alone would conflate. Device-initiated inter-node transfers are the exception to direct GPU-to-NIC posting: InfiniBand GPUDirect Async (IBGDA) is not available on the evaluated system, so NVSHMEM services them through a CPU proxy (Section~\ref{sec:ibgda-check}).

\subsection{Libraries and Drivers}

\begin{itemize}
    \item \textbf{NVIDIA driver:} 535.274.02, with the \texttt{nvidia\_peermem} module loaded for GPUDirect RDMA.
    \item \textbf{InfiniBand stack:} MLNX\_OFED 23.04-1.1.3.
    \item \textbf{CUDA toolchain:} NVHPC 24.5 with CUDA 12.4, for the CUDA benchmarks and aCG.
    \item \textbf{SYCL toolchain:} DPC++ 6.3 built from intel/llvm with the CUDA backend, GCC 12.2, and CUDA 12.2, for the SYCL benchmarks and solver.
    \item \textbf{MPI:} HPC-X 2.19, providing Open MPI over UCX, with UCC 1.4.0 as an optional collective component. It serves the CUDA and SYCL MPI paths and is the substrate of OSHMPI.
    \item \textbf{NCCL:} 2.18.5, for the direct NCCL path and beneath oneCCL.
    \item \textbf{NVSHMEM:} 2.11.0, for the host- and device-invoked SHMEM paths.
    \item \textbf{OSHMPI and oneCCL:} built from source at pinned revisions, including the NCCL and OSHMPI backend extensions of this thesis. The oneCCL/NCCL build launches and bootstraps with its bundled Intel MPI, while NCCL carries the payload.
\end{itemize}

Source-built components are identified by repository and branch in the artifact records; exact measured revisions are not available for every archived run.

\paragraph{MPI and OSHMPI.} Both use the same HPC-X installation and UCX settings, but map operations differently: MPI uses two-sided and collective calls, OSHMPI uses MPI RMA, so a shared transport does not make their costs comparable as interface overhead. UCC is enabled for the standalone allreduce and all-to-all sweeps and disabled for \texttt{moe} and \texttt{cg\_step}, whose small or variable-count exchanges fall where UCC is slower or unmeasured. This is a fixed policy per pattern rather than the better of two settings per point; its effect is quantified by the paired UCC comparison in Chapter~\ref{ch:m-results}.

\paragraph{NCCL.} Algorithm and protocol selection are left to NCCL. The oneCCL/NCCL stack is launched and bootstrapped through the Intel MPI bundled with its build, using the TCP provider across nodes; NCCL still carries the payload over InfiniBand.

\paragraph{NVSHMEM.} NVSHMEM bootstraps through MPI and dispatches its collectives to NCCL in the benchmark, so its collective results describe that dispatched path. The persistent device-invoked neighbor kernels limit the inter-node grid to eight blocks to bound the request load on the CPU proxy described in Section~\ref{sec:ibgda-check}. aCG instead disables NCCL dispatch, a difference Section~\ref{sec:acg-method} accounts for.

\paragraph{oneCCL adapters.}\label{sec:oneccl-method} Two stacks reach their backend through adapters contributed by this thesis, so each measures the adapted path rather than the backend alone. Both also run SYCL rather than CUDA, so a comparison with the direct backend changes the compute runtime as well.

\begin{itemize}
    \item \textbf{NCCL adapter.} Forwards oneCCL's group calls to NCCL, so a dependent send/receive batch is submitted as one group and completes asynchronously through the returned event.
    \item \textbf{OSHMPI adapter.} Maps collectives to OpenSHMEM operations where equivalents exist and composes the rest, for example all-to-all-v from puts and reduce-scatter from an allreduce. Operands are staged through a symmetric arena, and because the OpenSHMEM call blocks on the host, the returned event is already complete: completion is correct, but submission is no longer asynchronous. Staging and synchronization are inside the timed interval.
    \item \textbf{NVSHMEM adapter.} A runtime foundation only: it establishes communicator selection, bootstrap, lifecycle, and symmetric staging on one and two nodes, but its collective and point-to-point operations are unsupported. It contributes integration evidence and no measurements.
\end{itemize}

\subsection{Leonardo Considerations}\label{sec:ibgda-check}

\paragraph{No GPU-initiated network posting.} NVSHMEM can let a GPU kernel post InfiniBand requests directly through IBGDA, but this path is not available on the evaluated system. Table~\ref{tab:m-ibgda-check} compares the recorded driver configuration with the documented prerequisites \cite{nvidia_nvshmem_install_2026}: the base driver, peer-memory, and OFED requirements are met, but the peer-mapping and stream-memory settings IBGDA relies on are disabled or not reported. These observations explain the missing prerequisites; they do not by themselves prove why the transport is unavailable. A two-node diagnostic run confirmed that NVSHMEM selected the \texttt{ibrc} transport. Device-initiated inter-node requests in this thesis are therefore serviced by a CPU proxy, consistent with the lack of IBGDA support reported for Leonardo by Trotter et al.\ \cite{trotter_cpu-_2025}. Results for device-initiated NVSHMEM describe proxy-assisted networking, not GPU-posted networking.

\section{Benchmarks and Measurement Protocol}\label{sec:benchmark-method}

All benchmarks share one measurement contract, and differ only in the operation they time, the point at which each stack considers that operation complete, and how their payload is counted. This section first defines the shared contract, then describes each benchmark in the order of the evaluation levels: the four communication microbenchmarks, then the two application microbenchmarks. It closes with how samples are aggregated into the reported results.

\subsection{Common Protocol}\label{sec:completion-method}

\paragraph{Timing.} Every benchmark uses GPU-resident buffers with deterministic contents. After the warm-up iterations, each rank records the elapsed time of every timed iteration, from submission of the operation to its observed completion. Buffer initialization, the initial rank barrier, validation, and reporting are outside the timed interval. Because a distributed operation completes only when its slowest participant does, sample $i$ is the maximum over the $P$ ranks,
\begin{equation}
t_i=\max_{r\in\{0,\ldots,P-1\}}t_{i,r},
\end{equation}
and the trial latency is the arithmetic mean of that series. Ping-pong is the only exception, as described below.

\paragraph{Completion.} The timed interval ends at the completion boundary of each stack, which is part of the measured cost rather than an implementation detail. Table~\ref{tab:m-completion} summarizes the boundary each stack family uses; the benchmark descriptions below note where a pattern departs from it.

\paragraph{Correctness.} Each benchmark fills its send buffers with a known pattern and, after timing, every rank checks the data it received or computed against the expected result. The rank-local verdicts are combined into one global result; a cell that fails validation is not a performance result. The oneCCL adapters are additionally validated at the interface level: a complete batch must be submitted and its completion observed correctly, exercised through dependent send/receive batches, nested groups, deferred events, error propagation, and communicator reuse, with unsupported configurations rejected explicitly. Interface correctness and performance are therefore established separately.

\subsection{Communication Microbenchmarks}

The four microbenchmarks sweep powers of two over their size range and time one operation per iteration.

\subsubsection{Ping-Pong}

Rank 0 sends a buffer to rank 1, which returns the same payload; the exchange is dependency-ordered, since the reply cannot start before the message arrives. It runs on \texttt{1n2g} and \texttt{2n1g}, one link within a node and one across nodes.
\begin{itemize}
    \item \textbf{Timing:} only rank 0 records samples, and the reported latency is half the round trip. NVSHMEM is timed differently: all timed exchanges run inside one persistent device kernel whose duration is divided by the iteration count, so its result is an average with coarser sampling than the per-exchange samples of the other stacks. The OSHMPI exchange includes handshake barriers, which direct point-to-point signaling does not need.
    \item \textbf{Correctness:} rank 0 compares the returned buffer with the original payload.
    \item \textbf{Payload:} one direction of the exchange.
\end{itemize}

\subsubsection{Halo Exchange}

Each rank exchanges one boundary region with its left and right neighbors on a periodic ring, over every topology with at least two ranks.
\begin{itemize}
    \item \textbf{Timing:} each size is measured in two cases. An \emph{isolated} sample times one exchange and exposes submission and completion latency. A \emph{steady} sample times a batch of 100 consecutive exchanges and divides by the batch length, amortizing that cost over queued or persistent work. The two are different execution contracts, and the steady result is not an estimate of raw network latency. The MPI stacks wait for each exchange; NCCL and oneCCL/NCCL complete per batch; OSHMPI closes with a global barrier rather than neighbor signaling; NVSHMEM runs a cooperative device kernel with neighbor signals.
    \item \textbf{Correctness:} each rank checks both received regions against the markers its neighbors wrote.
    \item \textbf{Payload:} two sends and two receives per rank.
\end{itemize}

\subsubsection{Allreduce}

Each rank contributes a float32 buffer and receives the element-wise sum, over every topology including the single-rank control.
\begin{itemize}
    \item \textbf{Timing:} one completed reduction per sample. OSHMPI reduces CUDA symmetric operands directly in this benchmark.
    \item \textbf{Correctness:} rank $r$ fills its buffer with $r+1$, so every result element must equal $P(P+1)/2$.
    \item \textbf{Payload:} input bytes per rank; bus bandwidth applies the conventional ring factor $2(P-1)/P$, which normalizes traffic without implying the algorithm a library selected.
\end{itemize}

\subsubsection{All-to-All}

Each rank sends a distinct, equal-sized block to every rank, including itself, over every topology.
\begin{itemize}
    \item \textbf{Timing:} one completed exchange per sample. MPI and oneCCL issue a native all-to-all, while NCCL composes it from grouped point-to-point calls and OSHMPI from per-peer puts, so the same logical operation is implemented differently.
    \item \textbf{Correctness:} source $r$ fills its block for destination $d$ with $rP+d$, and every destination checks each received block.
    \item \textbf{Payload:} the size axis is bytes per peer, while bandwidth counts the whole per-rank send buffer including the self block.
\end{itemize}

\subsection{Application Microbenchmarks}

The application microbenchmarks keep the protocol above but time a workload's communication sequence instead of a single operation. Both run on every topology, including a single-rank control.

\subsubsection{MoE Dispatch and Combine}\label{sec:moe-method}

The MoE benchmark times one top-1 dispatch and its inverse combine, without expert computation. Every rank holds $T=16{,}384$ tokens of $H=256$ float32 features, each assigned to one expert rank; dispatch sends the tokens to their experts in variable-sized blocks, and combine returns each block unchanged. Three deterministic routing cases change only how tokens are distributed, never how many bytes are moved:
\begin{itemize}
    \item \texttt{uniform}: tokens are spread evenly across ranks, the case closest to the all-to-all benchmark.
    \item \texttt{locality80}: about 80\% of tokens stay on their source rank.
    \item \texttt{hotspot80}: about 80\% of tokens target rank 0, creating a deliberate incast onto one GPU and its network adapter.
\end{itemize}
A latency difference between routing cases is therefore attributable to distribution rather than volume. At one rank all three cases reduce to a local copy, so \texttt{1n1g} is a packing control rather than a network measurement.
\begin{itemize}
    \item \textbf{Timing:} one completed dispatch and combine per sample; routing, planning, and packing are outside timing. The MPI stacks issue two \texttt{MPI\_Alltoallv} calls, NCCL and oneCCL/NCCL issue grouped variable-count point-to-point exchanges, and both SHMEM stacks issue per-destination puts. OSHMPI closes each phase with a quiet, device synchronization, and a barrier; NVSHMEM closes with a quiet and one signal per peer actually exchanged with. The one-sided stacks have no collective algorithm to reorganize a skewed distribution, which \texttt{hotspot80} is designed to expose.
    \item \textbf{Correctness:} every rank checks the dispatch layout, token ownership, ordering, and payload, then checks that combine reproduced the packed send buffer exactly.
    \item \textbf{Payload:} useful application volume, $2 \cdot T H \cdot 4$ bytes per rank for dispatch and combine, including tokens that never leave their rank. It is not the traffic crossing a link.
\end{itemize}
MoE runs with UCC disabled (Section~\ref{sec:runtime-method}), a setting not tuned for the variable-count path it uses, so its MPI results describe one fixed configuration.

\subsubsection{CG Step}

The \texttt{cg\_step} benchmark extracts the communication structure of one conjugate-gradient iteration. An $S\times S$ grid, with $S$ from 512 to 8192, is distributed by columns. Each iteration packs the boundary columns, exchanges a nonperiodic west/east halo, applies a four-neighbor stencil, computes two local dot products, and performs two global sums of one double each, matching the two scalar reductions of a CG iteration. At fixed $S$, more ranks reduce local work; at a fixed rank count, a larger $S$ increases local work quadratically and halo length linearly. The benchmark keeps this operation sequence but omits vector updates, changing search directions, and convergence: the reduced scalars do not feed a next iterate, so it tests a communication/computation composition rather than the dependency graph of a full solver (Table~\ref{tab:m-cg-dependencies}).
\begin{itemize}
    \item \textbf{Timing:} each sample covers pack, halo exchange, unpack, stencil, both dot products, and both completed reductions. The MPI halo uses two serialized \texttt{MPI\_Sendrecv} calls. The archived OSHMPI stack reduces each scalar in host memory and does not copy the result back to the GPU. The NVSHMEM stack fuses the two sums into one two-element reduction. An optional second pass times pack, halo, compute, and reductions separately; it synchronizes at every phase boundary, so its phase sum is an instrumentation-sensitive diagnostic rather than a measure of overlap.
    \item \textbf{Correctness:} every rank checks its stencil slab against a host reference, and the two global dot products are checked. The archived OSHMPI check validates the host-side result only, so it does not cover returning that result to a GPU consumer.
    \item \textbf{Payload:} a nominal two-column halo, excluding the scalar reductions.
\end{itemize}

\section{Application Validation with aCG}\label{sec:acg-method}

The last evaluation level asks whether the benchmark observations hold in a complete application. It runs the aCG conjugate-gradient solver \cite{trotter_cpu-_2025} on large sparse problems with the same stacks, and compares its measured communication costs and backend ranking with those predicted by the microbenchmarks and \texttt{cg\_step}. Unlike the benchmarks, the solver introduces an irregular communication graph from a sparse partition, computation that can overlap communication, and convergence that determines how many iterations are run.

\subsection{Problems and Solver Variants}

The solver is evaluated on two symmetric positive definite matrices from the SuiteSparse Matrix Collection \cite{davis_suitesparse_2011}. Each is partitioned once with METIS, and the same partition is reused by every solver variant.

\begin{enumerate}
    \item \textbf{Bump\_2911:} 2\,911\,419 rows and 127\,729\,899 nonzeros.
    \item \textbf{Queen\_4147:} 4\,147\,110 rows and 329\,499\,284 nonzeros.
\end{enumerate}

Nonzero counts refer to the full symmetric matrix. Each matrix is solved with six variants:

\begin{enumerate}
    \item \textbf{MPI:} host-initiated CG, with halo exchange and reductions through CUDA-aware MPI.
    \item \textbf{NCCL:} host-initiated CG, with halo exchange and reductions through NCCL.
    \item \textbf{Host NVSHMEM:} host-initiated CG, with communication through NVSHMEM.
    \item \textbf{OSHMPI:} host-initiated CG, with an OpenSHMEM halo exchange contributed by this thesis and CUDA-aware MPI reductions.
    \item \textbf{Device NVSHMEM:} the monolithic solver, which runs the entire CG loop on the GPU with device-initiated NVSHMEM communication.
    \item \textbf{Single GPU:} a control without inter-rank communication.
\end{enumerate}

The multi-GPU variants run on 2, 4, 8, 16, and 32 GPUs, using the \texttt{1n2g}, \texttt{1n4g}, \texttt{2n4g}, \texttt{4n4g}, and \texttt{8n4g} topologies, with three allocations of three trials per configuration. All runs solve the same manufactured solution (seed 101) to a relative residual tolerance of $10^{-6}$, with no absolute tolerance and a limit of 100\,000 iterations. The retained archive contains 507 completed runs: 354 host-initiated, 90 device-NVSHMEM, and 63 single-GPU. Incomplete attempts are not counted as trials.

\subsection{Solver Environment}

The solver is built and run in the same software environment as the CUDA microbenchmarks, so that a difference between the benchmark and solver results is not a difference in library versions:

\begin{itemize}
    \item \textbf{Toolchain:} NVHPC 24.5 with CUDA 12.4.
    \item \textbf{Communication libraries:} HPC-X 2.19 for MPI, and the NCCL and NVSHMEM releases bundled with NVHPC 24.5, as in Section~\ref{sec:eval-environment}.
    \item \textbf{OSHMPI:} built from source against the same HPC-X installation.
    \item \textbf{Transport settings:} the Open MPI and UCX settings of Table~\ref{tab:m-runtime-settings}, taken from the benchmark configuration and shared by every communicator.
\end{itemize}

Three settings deliberately differ from the benchmark defaults, and each is accounted for in the comparison:

\begin{itemize}
    \item \textbf{Rendezvous threshold:} UCX switches to rendezvous at 16\,KiB instead of 1\,KiB. A separate control shows this changes the composite step by only about 2--3\%.
    \item \textbf{NCCL dispatch:} disabled beneath NVSHMEM, so host-NVSHMEM reductions use NVSHMEM's native path rather than the NCCL-dispatched path of the benchmarks. The default benchmark NVSHMEM reduction is therefore not used as a matched prediction.
    \item \textbf{UCC:} disabled, as in \texttt{cg\_step}, whose scalar reductions it matches.
\end{itemize}

\subsection{Metrics and Correctness}

\begin{itemize}
    \item \textbf{Solver time} is the time to solution. For the primary scaling view, following the reference study, the fastest residual-valid trial is selected per matrix, variant, and GPU count; all other trials are retained, and MPI variability is reported through allocation medians and ranges.
    \item \textbf{Throughput} separates execution cost from changes in iteration count. For standard CG with $K$ executed iterations, $n$ rows, and $\mathrm{nnz}$ nonzeros, the analytical work is
    \[
    W(K)=2(K+1)\,\mathrm{nnz}+2(5K+1)\,n,
    \]
    and per-GPU throughput on $P$ GPUs in time $T$ is $W(K)/(PT)$. It is derived from the operation count, not from hardware counters.
    \item \textbf{Correctness} requires successful completion and a final residual, relative to the initial residual, within the requested tolerance. Convergence is never inferred from the exit code alone, and a run with missing correctness fields is classified as unknown rather than failed. The error against the manufactured solution is kept as a separate numerical diagnostic.
    \item \textbf{Phase timers} have backend-dependent meanings and cannot be summed into a network-cost model. The halo timer covers only the wait remaining at halo-end, so OSHMPI's blocking communication appears mainly under \emph{other}; NVSHMEM may include communication in its SpMV interval; and the allreduce timer includes the wait for the slowest rank to arrive.
\end{itemize}

\subsection{Cross-Level Comparison}

The benchmark-to-solver comparison is made for the scalar reductions, the one operation both levels perform identically: two global sums of one double per iteration. The benchmark estimate is half of the \texttt{cg\_step} reduction phase at side 512. The solver measurement is the accumulated allreduce time divided by the recorded number of calls, which for $K$ iterations is $2K+2$ because the solver also reduces outside its main loop. MPI is paired with the MPI reductions of the OSHMPI variant, avoiding the variability of the MPI halo, and NCCL with the NCCL variant. The discrepancy over the five matched GPU counts is
\[
\mathrm{MAPE}=\frac{100}{5}\sum_{P\in\{2,4,8,16,32\}}
\left|\frac{\widehat{t}_P}{t_P}-1\right|.
\]
This is a descriptive check of one phase cost across scale, not a fitted prediction of total solver time. The pairing matches datatype as well as payload: an eight-byte float32 allreduce from the microbenchmark would match the size but not the operation.

Two variants limit what the comparison can claim:
\begin{itemize}
    \item \textbf{OSHMPI measures a halo only.} Its puts complete inside halo-begin, before local SpMV, and its reductions use MPI, so the OSHMPI label identifies a halo implementation, not an OpenSHMEM reduction.
    \item \textbf{Device NVSHMEM changes more than communication.} It also reorganizes computation and synchronization, so it is evaluated as a different execution model rather than a communicator substitution.
\end{itemize}

\paragraph{Supporting CUDA--SYCL comparison.} A separate report compares the CUDA solver with its SYCL port on Bump\_2911 at 1, 4, 8, and 16 GPUs, using solver-time medians over three repeats. The SYCL port is built with DPC++ 6.3, GCC 12.2, and CUDA 12.2 against Open MPI 4.1.6 and NCCL 2.22.3, so the comparison changes the MPI implementation and NCCL release as well as the programming model. Its CUDA parser also does not record the convergence flag, so its zero converged-count field reflects a missing classification rather than nonconvergence. The ratios are therefore reported as supporting implementation timings, not as a matched equal-accuracy comparison.

\section{Reproducibility and Evidence Boundaries}\label{sec:reproducibility}

All results reported in this thesis are provided in a supplementary archive distributed with it. The archive contains:
\begin{itemize}
    \item the exported benchmark results for every pattern, with trial-level records grouped by allocation;
    \item the completed aCG solver logs and the communication graphs of the sparse partitions;
    \item the reconciled summaries and tables used in Chapter~\ref{ch:m-results}, together with a manifest of source-file hashes;
    \item the scripts that regenerate those summaries, tables, and figures from the exported results.
\end{itemize}
Together with the benchmark tooling of Section~\ref{sec:harness}, which records each run's configuration, this allows both the analysis to be reproduced from the archive and the measurements to be repeated on the same system.

Three boundaries apply to the archived evidence:
\begin{itemize}
    \item \textbf{Revisions.} Repository revisions identify the imported archive, not necessarily the exact source of every measured run.
    \item \textbf{Snapshots.} The results come from more than one measurement snapshot. The allreduce and MoE results are from a later campaign than the other microbenchmarks, and the five-size \texttt{cg\_step} sweep is retained from the earlier campaign because its later re-run covers only one grid size. The manifest records which snapshot each pattern comes from.
    \item \textbf{Auxiliary controls.} The rail-count, scalar-placement, forced-algorithm, and dispatch controls survive as analysis summaries rather than complete trial datasets, and are reported without reconstructed error bars.
\end{itemize}
