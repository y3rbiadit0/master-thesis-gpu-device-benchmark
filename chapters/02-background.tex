\chapter{Background}\label{ch:m-problem}

This chapter establishes the conceptual framework used to interpret the measurements. An application's \emph{communication signature} comprises its operations, message sizes, rank placement, and dependencies. A programming interface expresses those requirements; a library implementation selects algorithms and protocols; and transport mechanisms map the resulting traffic to physical links. Performance depends on how these layers interact.

The discussion proceeds from interconnects and GPU execution to communication semantics, application dependencies, and library implementations. Throughout the thesis, \emph{model} denotes semantics such as two-sided message passing or one-sided PGAS; \emph{implementation} denotes a concrete library such as HPC-X MPI or NVSHMEM; and \emph{oneCCL backend} denotes an adapter beneath oneCCL. Transport frameworks such as UCX select lower-level mechanisms, including shared memory, CUDA IPC, TCP, and InfiniBand verbs. The chapter closes with performance concepts and the Leonardo hardware platform; experimental settings are recorded in Chapter~\ref{ch:m-methodology} and Section~\ref{sec:eval-environment}.

\section{GPU-Centric Communication and Interconnects}\label{sec:interconnects}

A multi-GPU application communicates within nodes and across a network between nodes. Each domain admits several payload routes and divisions of work between the GPU, CPU, and network interface controller (NIC). Hardware connectivity constrains these choices, while the application and communication stack determine which supported mechanisms are used.

\subsection{Invocation, Progress, and Memory Are Separate Axes}\label{sec:initiation-axes}

\emph{GPU-aware} describes an interface's ability to accept device buffers; \emph{GPU-initiated} describes where an operation is invoked. Neither term specifies who posts a network request or whether communication overlaps computation. Table~\ref{tab:m-initiation-axes} keeps these distinctions explicit. In particular, a CPU-launched communication kernel is not evidence that the application itself calls a communication API from GPU code, and a device-side call may still depend on a CPU progress thread \cite{unat_landscape_2026,hamidouche_kernel-initiated_2026}.

These dimensions must be identified together when interpreting a measurement. A GPU kernel may access peer memory directly within a node yet rely on a CPU proxy for a remote node, while a host-called operation may use the same registered memory as a device-called one. The NCCL discussion in Section~\ref{sec:xccl} illustrates these combinations through its device API and symmetric-memory support. The following subsections establish the intra-node and inter-node mechanisms on which such interfaces depend.

\subsection{Intra-Node Communication}\label{sec:intra-node}

\subsubsection{The Interconnect}

Within a node, GPUs communicate through PCI Express or a dedicated accelerator fabric. PCIe also connects storage and network devices, so peer traffic can share links and switches with other activity. NVIDIA's NVLink provides higher-bandwidth GPU connectivity, either through direct links or through NVSwitch; AMD systems use Infinity Fabric with xGMI links. In each case, peer-memory bandwidth remains distinct from the bandwidth of a GPU's local high-bandwidth memory (HBM) \cite{song_survey_2025}.

An important distinction is that per-device figures aggregate all of a GPU's links; they are not automatically the bandwidth available between one pair of GPUs. The A100 devices used in this work expose NVLink~3.0 as 12 links of 25\,GB/s per direction, giving 600\,GB/s of bidirectional endpoint bandwidth in total. Pair bandwidth depends on how those links are distributed and routed. NVSwitch provides switched connectivity, but a transfer remains bounded by endpoint, switch, and concurrent-traffic limits. The Leonardo Booster node described in Section~\ref{sec:leonardo} instead connects four GPUs directly, with four links per peer, giving a 200\,GB/s bidirectional theoretical ceiling for one pair -- one third of the per-device aggregate \cite{song_survey_2025,turisini_leonardo_2024}. The distinction matters whenever an aggregate specification is used as the reference for a point-to-point measurement.

Intra-node connectivity can be non-uniform: GPU pairs may have different direct links, routes, or proximity to a network adapter. Measurements on DGX and Summit systems demonstrate NUMA-like effects from these differences \cite{li_evaluating_2020}; characterization on Alps, Leonardo, and LUMI provides further evidence that placement must be included in a communication comparison \cite{desensi_exploring_2024}.

The practical consequence for this thesis is a bandwidth asymmetry of roughly an order of magnitude between the intra-node fabric and the inter-node network. A collective algorithm that ignores this asymmetry may become topology-limited regardless of its local efficiency. Topology-aware implementations therefore discover or inherit placement information and often use hierarchical schedules that separate intra-node and inter-node phases, as Section~\ref{sec:collective-algorithms} describes.

Payload route, memory allocation, process sharing, and access mechanism are separate properties. For example, CUDA interprocess communication (IPC) can make a peer allocation accessible across processes, after which either a copy operation or a GPU kernel may move the data. \paragraph{Host staging and mapped memory.} A staged transfer copies data from the source GPU to host memory and then to the destination GPU. With a non-GPU-aware MPI implementation, the application must perform these copies explicitly before and after communication on host buffers. A GPU-aware implementation may perform staging internally when a direct path is unavailable or unfavorable. Page-locked (pinned) host memory supports asynchronous device copies; when mapped for GPU access, it can also be read or written by a kernel. Mapped access replaces explicit copy calls with memory transactions across the host--device interconnect. It does not eliminate payload movement through host memory, and the number of transfers depends on where the producer and consumer operate \cite{nvidia_cuda_programming_2026}.

\paragraph{Peer access and bulk copies.} GPUDirect Peer-to-Peer allows supported GPU pairs to exchange data without host staging over NVLink or PCIe. Peer accessibility depends on topology, driver support, and access permissions. Once access is enabled, CUDA supports both bulk peer copies and kernel loads/stores to peer memory. These mechanisms can use the same physical route while incurring different launch and resource costs \cite{nvidia_cuda_programming_2026}.

\paragraph{Cross-process sharing.} In the one-rank-per-GPU execution model, allocations belong to different processes. CUDA IPC and shareable Virtual Memory Management (VMM) handles allow an owning process to export memory for a peer to import and map. VMM additionally provides allocation-level control over mappings and access permissions. These are ways to establish reachability, not distinct payload routes or requirements for symmetric allocation. Conventional peer access also permits remote kernel loads/stores without VMM \cite{nvidia_cuda_programming_2026}.

\paragraph{Library-managed access.} NVSHMEM and NCCL's Load/Store Accessible device-API mode establish peer mappings so that GPU code can access remote buffers. Their symmetric-memory contracts simplify locating corresponding buffers across ranks, but those contracts belong to the library interface rather than to peer access itself. Ordering, completion, and notification remain necessary before a receiver consumes remotely written data.

\paragraph{Fabric-assisted replication and reduction.} On systems supporting NVLink SHARP, multicast mappings and \texttt{multimem} instructions enable replication or reduction through the fabric \cite{shen_every_2026}. These mechanisms can reduce endpoint work and traffic for suitable collective phases. They cannot combine distinct all-to-all payloads into a common result. Leonardo's A100 nodes lack this fabric assistance, so it is relevant here as context for newer NCCL paths.

\subsection{Inter-Node Communication}\label{sec:inter-node}

\subsubsection{The Interconnect}

Across nodes, HPC systems commonly use InfiniBand or comparable RDMA-capable fabrics. Remote Direct Memory Access (RDMA) allows a network adapter to access registered remote memory without a matching receive or CPU copy at the target. Software still establishes registration, access rights, and synchronization. RDMA over Converged Ethernet (RoCE) provides related capabilities over a suitably configured Ethernet network. Both can be accessed through verbs interfaces, with performance dependent on adapters, routing, and congestion \cite{hamidouche_gpu-initiated_2025}.

GPU--NIC affinity matters: a nearby NIC can avoid additional PCIe or inter-socket traversal, while unfavorable placement can reduce peer-to-peer throughput \cite{hamidouche_gpu-initiated_2025}. The number and placement of adapters also bound network injection bandwidth and affect how libraries distribute concurrent transfers.

\subsubsection{Types of Inter-Node Communication}

Describing a library simply as ``GPU-side'' or ``CPU-side'' is imprecise, because a single communication call decomposes into several operations that may be performed by different actors. Unat et al.\ \cite{unat_landscape_2026} classify communication by \emph{who performs each operation}. Table~\ref{tab:m-comm-types} adapts this perspective to the paths discussed here, distinguishing host setup from steady-state invocation and network posting. Removing the CPU from the steady-state control path does not imply removing host-side memory registration or communicator creation.

\paragraph{Host-staged.} The payload is copied from the source GPU to host memory, sent across the network, and copied from host memory to the destination GPU. The application performs this staging with non-GPU-aware MPI; an accelerator-aware library may instead hide it internally. Sharing pinned buffers between the GPU runtime and NIC can avoid an additional host-to-host bounce copy, but does not remove the device--host and host--device payload transfers \cite{unat_landscape_2026}.

\paragraph{Host-posted GPU RDMA and proxy progress.} GPUDirect RDMA lets the NIC access registered GPU memory without moving the payload through host memory \cite{unat_landscape_2026,hamidouche_gpu-initiated_2025}. The CPU may post requests after a host API call or consume requests generated by a GPU kernel through a proxy queue. In either case, direct payload movement coexists with host-side control. Concurrent kernels must observe the platform's visibility and ordering rules before consuming incoming data; registration alone supplies no producer--consumer synchronization. Device communication libraries provide transport-specific completion and notification mechanisms for this purpose.

\paragraph{GPU-triggered.} In a host-prepared GPUDirect Async schedule, GPU code triggers network operations using descriptors constructed by the CPU. The device can ring a mapped NIC doorbell and wait for completion without returning control to the host for each operation \cite{agostini_gpudirect_2018,hamidouche_gpu-initiated_2025}. This reduces repeated host intervention for a known schedule, but does not give the device arbitrary request construction.

\paragraph{Kernel-initiated network posting.} GPU code can also construct and post requests whose targets and sizes are computed inside a kernel. NVSHMEM's IBGDA transport, NCCL's GDAKI backend using DOCA GPUNetIO, and ROC\_SHMEM's GPU-IB backend provide such paths \cite{unat_landscape_2026,hamidouche_kernel-initiated_2026}. They require device-accessible NIC control structures, suitable memory mappings, and compatible hardware and drivers. Exact prerequisites are release-specific. A supported proxy backend can preserve device-side invocation when direct posting is unavailable.

A library can expose several of these paths. In particular, the same device-side NVSHMEM call can use peer-memory access within a node and a CPU proxy across nodes. Identifying the actual path is therefore necessary before attributing a measured difference to GPU initiation.

\subsection{Abstraction Layers}

UCX and libfabric expose transport-independent primitives and select supported lower-level mechanisms. Communication libraries may use these frameworks, call verbs directly, or delegate operations to another library \cite{unat_landscape_2026}. For example, Open MPI can use UCX for point-to-point traffic and select UCC as a collective component; these are configuration choices rather than consequences of GPU awareness. OSHMPI implements OpenSHMEM over MPI, whereas NCCL and NVSHMEM provide their own transport selection. Two stacks may ultimately use the same links and still differ in scheduling, buffering, protocol, and progress.

\section{Heterogeneous Programming Models}\label{sec:programming-models}

The benchmark and solver must connect device memory and kernel execution to the communication library. CUDA supplies the native NVIDIA execution model; SYCL supplies the portable C++ model used by the alternative implementations. Their memory and dependency objects determine how communication can be inserted into an application schedule.

\paragraph{Kernels and execution groups.}
CUDA organizes kernel threads into blocks scheduled on streaming multiprocessors (SMs). Threads within a block can cooperate through shared memory and block barriers; blocks ordinarily execute independently. SYCL expresses a corresponding hierarchy of work-items, sub-groups, and work-groups, with backend-dependent mapping to hardware \cite{nvidia_cuda_programming_2026,hammond_comparative_2019}. These scopes matter when a communication primitive is called by one thread or cooperatively by a group.

\paragraph{Streams, queues, and events.}
A CUDA stream orders submitted kernels, copies, and stream-aware library operations. Work in different streams needs explicit dependencies where buffers are shared. A SYCL queue submits commands and returns events; an in-order queue preserves submission order, while an out-of-order queue requires dependencies through events or runtime-managed data access. Host submission can finish before device execution. Consequently, timing an enqueue call measures a different boundary from waiting on its completion event, and unnecessary host waits can serialize otherwise asynchronous work.

\paragraph{Device memory and unified shared memory.}
CUDA device allocations and SYCL device unified shared memory (USM) allocations provide pointers to GPU-resident storage. SYCL also provides host and shared USM, with different accessibility and placement properties. USM supplies a pointer-based interface; it does not imply that an arbitrary MPI implementation accepts the pointer, that the allocation is registered with the NIC, or that it meets a SHMEM symmetric-memory contract. The caller must also keep storage alive until asynchronous users have completed.

\paragraph{Native interoperability.}
SYCL implementations can expose backend-native objects. On a CUDA backend, obtaining the native stream allows an adapter to enqueue NCCL work in the device execution context used by SYCL. The adapter must still honor incoming dependencies and represent completion to subsequent SYCL commands. On Intel GPUs, lower-level runtime services are provided by Level Zero. HIP, used by the published aCG suite's AMD variants, provides a CUDA-like kernel and runtime interface within the ROCm ecosystem.

\paragraph{Persistent kernels and synchronization scope.}
A persistent kernel performs repeated work within one launch, allowing communication calls and waits to remain on the device. Removing repeated launches can reduce host-control overhead, but the kernel retains registers, shared memory, and SM capacity that could otherwise serve computation. A CUDA block barrier synchronizes only that block; a cooperative grid barrier requires a supported cooperative launch and a grid size compatible with its residency constraints. It does not synchronize ranks on other GPUs. Cross-rank phases require communication-library synchronization, with correct participation by the specified thread or group scope \cite{nvidia_cuda_programming_2026,ma_demystifying_2026}. Waiting threads must not occupy resources needed by work that produces their awaited condition. These constraints make launch shape, operation scope, and progress part of the persistent-kernel design.

\paragraph{Dimensions of portability.}
Source portability means that application code can target multiple platforms; build portability concerns toolchain and dependency availability; runtime interchangeability concerns backend selection; and performance portability concerns efficiency across targets. A SYCL application calling NCCL directly still depends on NVIDIA communication software. oneCCL supplies a common communication interface, but its backend must reconcile memory and execution semantics. CUDA--SYCL performance differences can arise in kernels, allocation, transfers, or host orchestration, with the balance depending on the implementation \cite{mijic_benchmark_2023,shen_sycl_2026}. The single-platform comparison here measures implementation performance retention rather than cross-vendor efficiency.

\section{Communication Operations}\label{sec:communication-operations}

Communication operations specify data movement, combination, or synchronization. Point-to-point operations concern pairs of ranks; collectives define a coordinated result over a group. Their completion contracts and surrounding dependencies determine when an application can use the result.

\subsection{Point-to-Point Operations}\label{sec:point-to-point}

A point-to-point transfer moves data from one rank to another. In a two-sided message-passing interface, a send supplies the source buffer and identifies the destination, while a matching receive supplies the destination buffer. Blocking and nonblocking forms govern when control returns to the caller; completion governs when buffers can be reused or their contents consumed. Completion of a send does not generally mean that the receiving application has already consumed the data.

One-sided operations express pairwise movement differently: a \texttt{put} writes to remote memory and a \texttt{get} reads from it without a matching receive for each transfer. The application must still establish valid remote addresses and coordinate ordering, completion, and buffer reuse. Section~\ref{sec:pgas} develops these requirements for OpenSHMEM. The same logical exchange can therefore be implemented using either matched messages or remote-memory operations, with different synchronization costs.

\paragraph{Pairwise exchange.} A ping-pong pattern sends a message to one peer and waits for a reply, exposing the startup and transfer costs of a dependency-ordered exchange. Larger or concurrently issued transfers place more emphasis on link bandwidth and the implementation's ability to sustain communication. Pairwise operations also support pipeline stages, where one rank forwards intermediate results to the next.

\paragraph{Neighbor exchange.} A halo exchange transfers boundary data between ranks adjacent in an application decomposition. Its peer set may be regular, as in a structured grid, or irregular, as in a partitioned sparse matrix. Its cost depends on the number of neighbors, message-size distribution, placement, and whether transfers are posted concurrently or serialized. In this thesis, halo exchange is assembled from pairwise operations rather than invoked through a neighborhood-collective API.

A halo expressed through nonblocking MPI receives and sends can post every transfer before waiting for completion. NCCL instead requires mutually dependent point-to-point operations to be submitted in a group, as discussed in Section~\ref{sec:nccl}. Identical peer sets therefore need different submission structures across these interfaces.

\subsection{Collective Operations}\label{sec:collectives}

\subsubsection{Definition and Participation}

A \emph{collective operation} is defined over the ranks of a communicator as one logical data transformation or synchronization. Participation does not imply simultaneous entry, and most collectives are not barriers. A blocking collective's return establishes its local completion contract; a nonblocking collective establishes that contract when its request completes. A stream-enqueued collective instead completes at the corresponding device execution boundary.

All ranks must issue compatible collective calls in an order permitted by the interface. This matching lets an implementation treat the operation as one scheduled entity rather than as independent transfers that merely happen to produce the same final layout.

A collective specifies a result rather than an algorithm. An allreduce, for example, can use a ring or a tree to produce the same logical reduction. Its schedule determines communication rounds, traffic distribution, and resource use; Section~\ref{sec:collective-algorithms} develops these choices.

\subsubsection{Patterns and Structural Attributes}

Collective patterns describe how sources, destinations, and results are related across the participating ranks. Four structural attributes govern both the cost of an operation and the difficulty of implementing it well.

\paragraph{Rooted or non-rooted.} Broadcast, reduce, scatter, and gather single out one rank as source or destination. Their semantics make them sensitive to where the root sits in the topology, although an implementation may distribute forwarding or reduction work across other ranks. Barrier, allgather, allreduce, reduce-scatter, and alltoall have no designated root. This semantic symmetry does not guarantee balanced traffic, particularly when contribution sizes or physical links differ.

\paragraph{Personalized or non-personalized.} Broadcast and allgather deliver a common final buffer to their recipients, allowing identical data to be forwarded or replicated. Scatter, reduce-scatter, and alltoall deliver destination-specific data. This personalization is independent of reduction: reduce-scatter combines contributions before distributing distinct slices. In alltoall, by contrast, the distinct payloads must be preserved, so they cannot be merged into a shared result. Its many-peer traffic can stress injection rate, message processing, and network contention.

\paragraph{Reducing or purely moving.} Allreduce, reduce, and reduce-scatter apply an operator to the data in flight, which introduces two complications absent from pure data movement. Computation must be placed somewhere -- on the GPU, on the host CPU, or inside the network -- and staging a GPU reduction through the host adds transfers and synchronization that a GPU-native implementation may avoid. Furthermore, floating-point reduction is not associative, so the numerical result depends on the order in which partial sums are combined; changing algorithm, rank count, or chunk size can change the last bits of the answer. For an iterative solver this can alter the iteration count required to reach a residual threshold, so Chapter~\ref{ch:m-results} treats convergence as something to verify rather than assume when the backend changes.

\paragraph{Uniform or vector.} Uniform forms use counts fixed by the operation: for alltoall, each source sends the same count to every destination. Vector variants relax different dimensions. Allgatherv permits source-dependent contribution sizes, reduce-scatter variants permit rank-dependent result sizes, and alltoallv permits a distinct count and displacement for every source--destination pair. This distinction matters when volumes are data-dependent. A uniform interface may require padding to a capacity or a preliminary size exchange, whereas a variable-count interface can represent the resulting layout directly.

The operations can also be composed: a reduce-scatter followed by an allgather produces an allreduce result when counts and layouts agree. All-to-all represents the opposite traffic requirement, preserving a distinct segment for each of $P-1$ remote destinations per rank. These structures determine which aggregation and scheduling opportunities an implementation can exploit.

\subsection{Completion, Ordering, and Progress}\label{sec:completion-semantics}

Several distinct boundaries are relevant to a transfer:
\begin{itemize}
\item \textbf{Local completion} permits the caller to reuse the operation's local buffers according to its contract. An MPI send completion, for example, permits source-buffer reuse but does not establish that the receiver has consumed the message.
\item \textbf{Remote completion} establishes that an update has reached the destination memory as defined by the communication interface. A receiving GPU must also observe the required memory-ordering and visibility rules before accessing it.
\item \textbf{Notification} tells the receiver that data is ready. A flag or signal must be ordered after the payload it announces; remote completion alone does not tell the receiver when to proceed.
\item \textbf{Ordering} constrains the relative observation of operations. It need not wait for those operations to finish or synchronize all participating ranks.
\item \textbf{Collective synchronization} coordinates a group of ranks. A barrier establishes participation, but its treatment of outstanding communication depends on the interface; it must not be substituted for a completion primitive without checking that contract.
\end{itemize}

\emph{Progress} is the work that advances an operation after submission, such as matching requests, posting descriptors, transferring payload, or detecting completion. A nonblocking interface permits the caller to continue but does not necessarily guarantee autonomous progress. Communication can overlap GPU computation through CPU polling, a progress thread, GPU execution, or NIC offload, provided the required resources remain available. A measurement must therefore state both its completion boundary and the progress mechanism active inside that interval.

\subsection{Application Communication Signatures}\label{sec:workload-patterns}

A communication signature combines operation sequence, message-size distribution, rank placement, peer set, and dependencies. A small reduction whose result is needed immediately stresses startup and completion latency; a large transfer that overlaps independent kernels stresses sustained progress and resource sharing. The following workloads motivate the benchmark's operation mix.

\subsubsection{Distributed Learning Workloads}

\paragraph{Data-parallel and sharded training.} Data parallelism replicates a model and combines gradients through allreduce operations over parameter buckets. Large buckets emphasize bandwidth, while small buckets and fine-grained overlap expose startup and scheduling costs. Sharded training exposes reduce-scatter and allgather separately for partitioned optimizer states and parameters \cite{weingram_xccl_2023}.

\paragraph{Mixture-of-Experts.} Under expert parallelism, token dispatch and result combination form personalized redistributions among devices. Uneven routing produces variable pairwise counts; implementations may pad to a fixed capacity or exchange counts and transfer only assigned tokens \cite{cai_survey_2025,huang_toward_2024}. These alternatives motivate uniform all-to-all and alltoallv tests. Specialized libraries such as DeepEP also implement sparse dispatch and combine with device-side primitives over symmetric-memory substrates, so a dense collective benchmark represents only part of this workload \cite{ma_demystifying_2026,hamidouche_gpu-initiated_2025}.

\paragraph{Latency-sensitive inference.} Tensor-parallel decoding can place repeated small collectives on the token-generation critical path, making startup latency important even when communication volume is modest \cite{shen_every_2026}. Training, MoE, and inference provide motivation for the measured regimes; complete learning applications are outside the evaluation scope.

\subsubsection{Conjugate Gradient: Communication and Dependencies}\label{sec:cg-background}

Standard Conjugate Gradient (CG) solves $Ax=b$ for a symmetric positive-definite matrix $A$. At iteration $k$, it maintains an approximation $x_k$, residual $r_k=b-Ax_k$, and search direction $p_k$. Sparse matrix--vector multiplication (SpMV) and vector updates have low arithmetic intensity, while global dot products create repeated synchronization dependencies. These properties make CG sensitive to both memory bandwidth and communication latency \cite{trotter_cpu-_2025}.

With a row partition across ranks, rank $i$ computes its product contribution as
\[
q_{k,i}=A_{ii}p_{k,i}+\sum_{j\ne i} A_{ij}p_{k,j}.
\]
It owns $p_{k,i}$, but must obtain the entries of $p_{k,j}$ referenced by its off-rank nonzeros. These entries form a halo. The sparse partition determines the neighbor set and payload distribution, which need not resemble a regular two-neighbor exchange. The locally owned-column product $A_{ii}p_{k,i}$ can proceed while remote entries arrive, if the halo implementation permits progress during that computation.

Dot products combine local partial sums through global reductions. In double precision, each of the two scalar sums carries eight bytes per rank.

This schedule explains why tiny reductions can limit scaling even when halo payloads are much larger: the scalar results directly gate subsequent work, while some halo time may be hidden by SpMV. Pipelined variants alter the recurrences to create additional overlap, and a monolithic device-side solver changes how phases are launched and synchronized \cite{trotter_cpu-_2025}. The composite \texttt{cg\_step} captures the halo-plus-two-reductions skeleton, while complete aCG execution supplies the irregular partition, computation, and convergence behavior.

In floating-point arithmetic, changing reduction order can change the computed coefficients and the number of iterations needed to meet a residual tolerance. A backend comparison must therefore report convergence and distinguish per-iteration cost from total time to solution. The recursively updated residual can also differ from an explicitly recomputed $b-Ax_k$, so the residual definition belongs in the correctness policy.

\section{Communication Libraries and Backends}\label{sec:backends}

The evaluated stacks draw on MPI, OpenSHMEM, and specialized collective libraries. MPI and OpenSHMEM are specifications with multiple implementations; NCCL, RCCL, and oneCCL are libraries with related but distinct interfaces. Their operation coverage, memory contracts, execution ordering, and progress mechanisms determine how they can implement the communication signatures above.

\subsection{Two-Sided Message Passing: MPI}\label{sec:mpi}

\subsubsection{The MPI Standard}

MPI defines send/receive communication, collectives, and one-sided RMA. The send/receive operations used by the direct MPI paths here are \emph{two-sided}: messages match through source, destination, tag, and communicator rules. A standard-mode send may complete locally before its receive is posted if the implementation buffers the message. MPI's separate RMA interface exposes memory windows for remote access and provides the substrate used by OSHMPI.

\subsubsection{GPU-Aware MPI and Its Implementations}

\emph{GPU-aware MPI} extends implementations so that device pointers may be passed directly to MPI calls. This removes explicit staging from application code and permits an implementation to use GPUDirect RDMA or intra-node peer access, but accepting a device pointer does not guarantee that a direct path was selected: the build, transport provider, message size, and topology may still lead to internal staging.

For example, a halo exchange posts an \texttt{MPI\_Irecv} for each neighbor, followed by corresponding \texttt{MPI\_Isend} operations and an \texttt{MPI\_Waitall}; a global dot product uses \texttt{MPI\_Allreduce}. An eager protocol may send data before receiving explicit readiness from the target, whereas rendezvous exchanges coordination messages before the bulk transfer. Either protocol can use different memory and transport mechanisms. The threshold between them can therefore change both latency and the opportunity for overlap.

The first limitation is integration with the GPU execution model \cite{unat_landscape_2026}. GPU work is submitted to streams, which order operations while allowing the host to run ahead. Standard MPI does not make a request an operation in a CUDA or SYCL stream: explicit synchronization is needed before MPI accesses data produced on a stream and before a stream consumes received data. Nonblocking MPI and independent buffers can still provide overlap, and implementation extensions can reduce host intervention, but the standard interface does not directly express stream dependencies. Stream-aware proposals such as MPIX extensions and device-initiated MPI calls address this gap but are not part of the evaluated standard path.

The second limitation is implementation variability. Without accelerator-aware collective components, an MPI implementation may stage reduction data through host memory or execute the reduction on the CPU, adding transfers that a GPU-native implementation avoids \cite{unat_landscape_2026}. Reported comparisons nevertheless do not favor one family uniformly: MPI often performs well for point-to-point operations, while specialized collective libraries often perform well for GPU collectives, with crossovers depending on system, node count, message size, and implementation \cite{unat_landscape_2026}. MPI remains a useful baseline because its standard is vendor-neutral and broadly available.

MPICH, Open MPI, and vendor distributions such as HPC-X and Intel MPI differ in accelerator support, transports, progress, and collective selection. The direct CUDA and SYCL MPI paths here use HPC-X over UCX. Intel MPI appears in the oneCCL/NCCL launch and bootstrap path, not its NCCL payload path. Section~\ref{sec:eval-environment} records the versions and roles of these components.

UCC is a collective-library component that Open MPI can select in place of its native collective modules. Its architecture separates collective layers from transport layers; in the installed configuration, the basic collective layer dispatches CUDA-buffer operations to the UCP transport layer, which in turn uses UCX endpoints and tagged communication over the configured shared-memory, CUDA, and InfiniBand transports \cite{venkata_ucc_2024,openucx_ucc_source_2026}. UCC therefore does not replace UCX in this stack. It replaces Open MPI's collective schedule while retaining UCX/UCP as the data-movement substrate.

\subsection{One-Sided PGAS Models: OpenSHMEM and Its Implementations}\label{sec:pgas}

In a Partitioned Global Address Space model, processes can access designated remote memory through operations such as \texttt{put} and \texttt{get}. The target application need not post a matching receive for each transfer, although setup, synchronization, and implementation progress may still require its participation.

\subsubsection{The OpenSHMEM Standard}

OpenSHMEM standardizes a PGAS API and memory model. GPU allocation support and device-callable operations are properties of its implementations and extensions.

The central concept is \emph{symmetric memory}: corresponding objects exist on participating processing elements (PEs), and a local symmetric address together with a PE identifier identifies the remote object. Symmetric heap allocations are collective and must satisfy matching allocation requirements; the interface does not require the application to assume identical virtual addresses in different processes. RMA requires the remotely accessed operand to be symmetric, while requirements on local operands and collective buffers depend on the operation and implementation. An adapter accepting ordinary application buffers must stage operands that do not meet these contracts. The oneCCL/OSHMPI backend provides that staging path.

The completion distinctions in Section~\ref{sec:completion-semantics} have concrete counterparts in OpenSHMEM. A blocking put permits local source reuse when it returns, but remote delivery may still be pending. A \texttt{fence} orders preceding puts before subsequent puts to the same destination within its defined scope; it need not wait for delivery. A \texttt{quiet} waits for completion of the outstanding operations covered by its context. Neither operation alone notifies the receiver that it should consume the data \cite{openmpi_shmem_fence_2026,openmpi_shmem_quiet_2026}.

A put followed by an appropriately ordered signal, or a combined put-with-signal primitive, lets the receiver wait for a ready condition before accessing the payload. Buffer reuse requires a further guarantee that the receiver has finished consuming the previous data. Barriers can coordinate phases, while peer acknowledgments and suitably synchronized alternating buffers can avoid global synchronization. Modern OpenSHMEM collectives operate on \emph{teams}, analogous to communicators; older interfaces use active sets. Device implementations additionally specify which threads participate and which host- or device-issued operations a completion primitive covers \cite{ma_demystifying_2026,ravi_unified_2026}.

\subsubsection{Implementations}

NVSHMEM and OSHMPI are evaluated directly. ROC\_SHMEM and Intel SHMEM provide architectural context for GPU-side execution on other vendors' systems.

\paragraph{NVSHMEM (NVIDIA).}
NVSHMEM \cite{nvidia_nvshmem_repo} provides a device-resident symmetric heap allocated collectively through \texttt{nvshmem\_malloc}, with matching sizes across PEs. Device-side signaling, waits, and barriers allow distributed phases to remain within GPU execution rather than returning to the host for each synchronization \cite{unat_landscape_2026}.

NVSHMEM exposes ordinary host operations, separate stream-ordered extensions in the \texttt{nvshmemx\_*\_on\_stream} family, and device-callable operations at thread, warp, or block scope \cite{ma_demystifying_2026}. The on-stream family enqueues work from the host in a CUDA stream; device calls originate inside a kernel. For directly mapped peers, RMA can use loads/stores against the peer heap. Network requests can instead be posted through IBGDA or consumed by a CPU proxy. Proxy service and request granularity can limit throughput even though the application invokes communication on the GPU \cite{unat_landscape_2026}.

Two implementation properties are directly relevant to interpreting the NVSHMEM benchmarks. First, teams -- NVSHMEM's equivalent of communicators -- are lightweight handles rather than full runtime contexts, and a team cannot safely be used by concurrent collective invocations from the same PE, because the runtime associates a single set of synchronization state and scratch storage with each team \cite{ma_demystifying_2026}. Serializing operations on a team is therefore a correctness requirement, not a conservative choice. Second, arbitrary team construction is a runtime-version-dependent capability, which constrains how application communicators can be mapped onto NVSHMEM teams.

\paragraph{ROC\_SHMEM (AMD).}
ROC\_SHMEM, developed as rocSHMEM within the ROCm systems repository, provides device-side one-sided communication for AMD GPUs \cite{amd_rocshmem_repo}. Its GPU-IB and reverse-offload paths illustrate the same distinction between direct GPU posting and host-proxy progress. Correct visibility of incoming network writes depends on the backend's ordering and synchronization mechanisms, as it does for NVIDIA implementations \cite{unat_landscape_2026}.

\paragraph{Intel SHMEM.}
Intel SHMEM combines OpenSHMEM-style communication with device calls inside SYCL kernels \cite{intel_ishmem_repo,brooks_intel_shmem_2024}. The implementation described by Brooks et al. uses peer mappings and Level Zero for intra-node transfers, and a host proxy to an OpenSHMEM runtime for inter-node communication. OSHMPI is identified as a possible alternative proxy runtime. Its work-group-scoped operations provide an analogue to NVSHMEM's cooperative operation scopes. This architecture demonstrates how a portable compute interface can coexist with implementation-specific memory mappings and progress.

\paragraph{OSHMPI (portable, over MPI).}
OSHMPI implements OpenSHMEM over MPI RMA and collective operations. Its progress and data movement depend on the underlying MPI implementation; GPU support additionally requires suitable device-memory capabilities and allocation extensions. The direct path evaluated here uses a CUDA symmetric space for halo buffers, while the oneCCL adapter supplies symmetric staging for ordinary buffers. This makes OSHMPI a useful case for examining how a common one-sided interface maps onto host-driven MPI mechanisms. The application-specific choice to retain MPI scalar reductions is described in Section~\ref{sec:acg-method}.

\paragraph{Diverging GPU extensions.} Common OpenSHMEM origins do not imply identical GPU contracts. Implementations differ in allocation placement, symmetric-operand requirements, operation scopes, capability queries, and stream- or queue-ordered completion. Ravi et al. document these differences and propose a unified GPU-aware extension \cite{ravi_unified_2026}. Adapters must therefore check the concrete implementation's memory and participation requirements rather than infer them from API names alone.

\subsubsection{Programming Trade-offs}

One-sided access can express irregular writes without posting a receive for every message, but the application must manage remote offsets, capacity, notification, and safe reuse. Device-side variants add the choice of thread or group scope and must preserve progress within persistent kernels. Integrating communication into computation can also make phase attribution harder for kernel-based profiling. These requirements are the qualitative programming evidence examined alongside timing in RQ2 \cite{unat_landscape_2026,trotter_cpu-_2025}.

\subsection{Collective Communication Libraries: the xCCL Family}\label{sec:xccl}

The xCCL family specializes in collective communication for accelerator systems \cite{weingram_xccl_2023}. NCCL targets NVIDIA GPUs, RCCL targets AMD GPUs, and oneCCL provides a common interface with multiple implementation paths.

The original campaign's NCCL and oneCCL/NCCL interfaces are host-initiated and asynchronous with respect to a device stream or queue: the host enqueues communication and can continue without waiting for completion. This does not describe every oneCCL backend: the OSHMPI mapping is blocking. Topology handling is also implementation-specific. NCCL builds logical topologies and selects algorithms internally, while middleware such as oneCCL can delegate transport discovery and collective choices to lower layers. The application-facing API therefore hides different progress and selection mechanisms.

\subsubsection{NCCL (NVIDIA)}\label{sec:nccl}
NVIDIA's Collective Communication Library \cite{nvidia_nccl_repo} supplies topology-aware communication for NVIDIA GPUs. The NCCL~2.18.5 host interface used in the main campaign exposes allreduce, broadcast, reduce, allgather, reduce-scatter, and point-to-point send/receive. Communicators are initialized using a shared unique identifier or convenience routines for ranks managed within one process \cite{hu_demystifying_2025}.

\paragraph{Interface.} Relative to the MPI examples above, an NCCL allreduce expresses the same global reduction but enqueues it on a CUDA stream, so it is ordered with kernels and copies on that stream without requiring a blocking host call. A halo has no native neighborhood collective in the host API and is instead expressed as grouped \texttt{ncclSend}/\texttt{ncclRecv} operations. This narrower surface lets NCCL specialize aggressively for GPU topology, but it also means that operation coverage and grouping semantics form part of the comparison.

\paragraph{Algorithms, channels, and protocols.} In the legacy NCCL path analyzed by Hu et al., collectives are composed from reusable primitives over logical ring and double-binary-tree topologies established at communicator creation \cite{hu_demystifying_2025}. Work is divided into \emph{channels}, each operating on a disjoint buffer slice and generally launched as a CUDA block. Multiple channels help saturate links and can spread traffic across network adapters, while excessive channel counts add resource and synchronization overhead. Other NCCL versions and platforms may expose additional algorithms, including hardware-assisted and symmetric-memory paths, so ring and tree should be read as the principal algorithms of the analyzed path rather than the complete current search space.

Orthogonally to the algorithm, the analyzed legacy path selects among Simple, LL, and LL128 protocols, summarized in Table~\ref{tab:m-nccl-proto}. The choice trades payload efficiency against synchronization cost and is constrained by hardware: LL128 depends on write-atomicity properties that are not available on every route \cite{hu_demystifying_2025}.

\paragraph{Selection is a runtime decision.} The preceding components form a search space rather than one fixed NCCL implementation. Logical topologies are established at communicator creation from discovered connectivity. For each invocation, the tuning model considers the collective, message size, system topology, GPU architecture, modeled performance, and resource constraints when selecting an algorithm and protocol. It then chooses how many pre-established channels to activate based on the strategy, payload, available bandwidth, and configured resources \cite{hu_demystifying_2025}. Consequently, the same API call can map to a different schedule when message size, placement, or hardware changes.

A performance crossover can therefore reflect an algorithm or protocol switch while the physical network remains unchanged. Tuning controls and their effects are release-dependent, so interpretation requires the library version and runtime configuration.

\paragraph{Version-dependent collective coverage.} NCCL~2.18.5 has no native all-to-all entry point, so the benchmark composes it from grouped sends and receives. NCCL~2.31.2 documents \texttt{ncclAlltoAll} explicitly \cite{nvidia_nccl_collectives_2026}. An operation name therefore needs its API version and submission path to identify what was measured.

\paragraph{Grouped submission.} NCCL provides \texttt{ncclGroupStart} and \texttt{ncclGroupEnd}, which defer a sequence of operations until the group closes. Aggregation can reduce launch overhead and assign grouped point-to-point transfers to separate channels where possible \cite{hu_demystifying_2025}. For mutually dependent NCCL sends and receives, grouping is also required so that the runtime observes the full batch before execution. This requirement is specific to NCCL's submission semantics; a correct nonblocking MPI halo exchange does not require the same API. The grouped-operation contribution of this thesis propagates the group lifecycle through the oneCCL NCCL backend.

\paragraph{Device-initiated NCCL.} NCCL~2.28 introduced a device-side API allowing user kernels to invoke communication primitives. Its modes provide a concrete example of the separate invocation, progress, and memory axes introduced in Section~\ref{sec:initiation-axes}. LSA (Load/Store Accessible) provides peer-memory access over supported NVLink or PCIe paths. Multimem provides hardware multicast and reduction through NVLink SHARP, while GIN (GPU-Initiated Networking), documented from 2.28.7, provides network RDMA \cite{hamidouche_kernel-initiated_2026,nvidia_nccl_device_2026}. GIN supports a GDAKI backend, where GPU code posts network work through DOCA GPUNetIO, and a proxy backend, where CPU threads consume GPU-generated requests. Both provide device-side invocation; only the former removes CPU request posting from the steady-state network path. Their requirements and performance are release- and platform-dependent.

The device API uses collectively registered symmetric windows, adopting memory-access ideas associated with PGAS systems \cite{hamidouche_gpu-initiated_2025}. Such registration can also accelerate host-called collectives, so registered buffers alone do not identify device initiation \cite{nvidia_nccl_registration_2026}. Likewise, LSA reachability does not imply Multimem support. These distinctions govern the separate preliminary version and memory-path comparison in Section~\ref{sec:nccl-preliminary-results}; the main campaign uses host-initiated NCCL calls.

\subsubsection{RCCL (AMD)}\label{sec:rccl}
RCCL provides an NCCL-compatible collective interface for AMD GPUs \cite{amd_rccl_2026,amd_rccl_repo}. Its implementation accounts for AMD execution resources and Infinity Fabric topology, so API similarity does not imply identical algorithms or performance. It supplies context for the published cross-vendor aCG study but is not measured on Leonardo.

\subsubsection{oneCCL (multi-vendor)}\label{sec:oneccl}
oneCCL is the oneAPI ecosystem's collective library, maintained by the UXL Foundation \cite{uxl_oneccl_2026}. It provides a common interface for supported CPU and accelerator paths. Communicators identify participating ranks and device contexts; streams carry execution context; and operations return events representing completion. The interface supports asynchronous execution, although a particular backend may complete work before returning. Its operation surface includes allgather(v), allreduce, alltoall(v), barrier, broadcast, reduce, reduce-scatter, and point-to-point communication \cite{weingram_xccl_2023,unat_landscape_2026}.

oneCCL combines native collective implementations with delegation to other libraries. Its native paths use an Abstract Transport Layer (ATL) over MPI or libfabric, while SYCL and Level Zero support Intel GPU execution and data movement \cite{unat_landscape_2026}. Alternative backends can delegate operations to NCCL or to the SHMEM adapters developed here. Backend availability remains a build-time dependency even when the application-facing API is unchanged.

The same public call can nevertheless have different execution behavior. With the NCCL backend, an allreduce is enqueued on a native CUDA stream and returns an event tracking pending work. With the OSHMPI adapter, dependencies are completed before the blocking host operation and the returned event is already complete. Both must satisfy the caller's dependency and buffer-lifetime requirements, but only the former preserves asynchronous submission. Chapter~\ref{ch:m-methodology} describes the adapters and the separately validated NVSHMEM runtime foundation.

\subsection{Collective Algorithms and Runtime Selection}\label{sec:collective-algorithms}

The libraries above translate operation semantics into communication schedules. The same operation admits many schedules, and choosing among them is a major performance lever. The recurring algorithms illustrate why a common API can exhibit different behavior across message sizes and topologies.

A \emph{ring} arranges $P$ ranks in a logical cycle and moves data in $2(P-1)$ steps for an allreduce, with each rank sending a $1/P$ slice at every step. For an evenly partitioned buffer of $n$ bytes, each rank sends $2n(P-1)/P$ bytes and receives the same amount over the complete operation. Each volume approaches $2n$ as the rank count grows, while the number of steps grows linearly in $P$, favoring large messages over small ones \cite{weingram_xccl_2023}. A \emph{binomial tree} inverts the trade-off, completing in $O(\log P)$ steps and therefore favoring short messages, at the cost of lower link concurrency and concentrated traffic near interior nodes. NCCL's \emph{double binary tree} overlays two trees so that the leaves of one are interior nodes of the other, giving logarithmic latency while keeping nearly every rank active \cite{weingram_xccl_2023,hu_demystifying_2025}. \emph{Recursive doubling} and \emph{recursive halving} pair ranks at exponentially changing distances; combining a recursive-halving reduce-scatter with a recursive-doubling allgather yields Rabenseifner's allreduce.

For all-to-all, \emph{Bruck's algorithm} trades local data reorganization and additional forwarded data for fewer communication rounds, while pairwise exchange sends directly to one peer per round \cite{bruck_alltoall_1997,pjesivac_mpi_collectives_2007}. Those trade-offs do not establish a GPU performance ranking: the cost of local memory operations and the available topology remain part of the implementation. Finally, \emph{hierarchical} schedules decompose an operation into intra-node and inter-node phases, allowing local aggregation where the operation permits it and accounting for the different bandwidths of the two domains.

Libraries select schedules using runtime heuristics or explicit controls. Open MPI's tuned component uses fixed and dynamic decision rules \cite{pjesivac_mpi_collectives_2007,openmpi_alltoall_source_2026}; NCCL selects algorithms, protocols, and channel counts. PICO and TuCCL show that alternative configurations can outperform defaults for particular workloads and systems \cite{pasqualoni_pico_2026,li_tuccl_2025}. Their detailed findings are discussed in Chapter~\ref{ch:m-related}.

\section{Compilers and Toolchains}

Compiler interoperability determines whether a communication library can use the application's device code and execution objects. Two interfaces matter here: host-side access to native runtime objects and device linking of GPU-callable library functions.

\paragraph{DPC++.}
DPC++ is an LLVM-based SYCL implementation with a CUDA backend \cite{intel_llvm_sycl_63}. Its native-object interoperability allows the oneCCL NCCL adapter to obtain a \texttt{cudaStream\_t} from the SYCL execution context. This is host-side interoperability: it does not by itself make an NVSHMEM device function callable from a SYCL kernel.

\paragraph{NVCC.}
The direct CUDA implementations use NVCC. Calling NVSHMEM device functions requires a compatible device compilation and link process, including relocatable device code and the NVSHMEM device library. A narrow NVCC-compiled adapter can instead expose host-callable entry points to DPC++ code. The validated on-stream interoperability experiment in Chapter~\ref{ch:m-methodology} uses this separation.

\paragraph{Host compilers.}
The host compiler and C++ standard library must be compatible with both device toolchains and the communication libraries. Section~\ref{sec:eval-environment} records the concrete compiler, toolkit, and library versions used in the campaigns.

\section{Communication Performance Characteristics}

\paragraph{Analytic models.}
The cost of a single transfer is conventionally modeled by the Hockney model as $T(m) = \alpha + \beta m$, where $\alpha$ is startup latency and $\beta$ reciprocal bandwidth. Small messages are dominated by $\alpha$, while large messages approach the $\beta m$ regime. Richer models add structure: LogP separates latency, per-message overhead, and the minimum gap between messages, while LogGP adds a per-byte gap parameter for long messages \cite{rico-gallego_survey_2019}. In this thesis these models are interpretive frames used to distinguish startup, injection, and bandwidth effects rather than predictive models fitted to every backend.

\paragraph{Collective cost.}
For the ring allreduce in Section~\ref{sec:collective-algorithms}, a simple model is
\[
T_{\mathrm{ring}}(n,P)\approx 2(P-1)\alpha+\frac{2(P-1)}{P}n\beta,
\]
where $n$ is the input size per rank. This expression omits reduction arithmetic, contention, pipelining, and launch costs, but shows how a nearly constant per-rank traffic volume can coexist with a latency term that grows with rank count. Tree-based algorithms reduce the round count, with different traffic and concurrency trade-offs \cite{weingram_xccl_2023}.

\paragraph{Reported bandwidth.}
\emph{Algorithm bandwidth} divides a stated logical payload by elapsed time. \emph{Bus bandwidth} applies an operation- and rank-count-dependent normalization, for example $2(P-1)/P$ for allreduce in the usual NCCL convention. It is an estimate of communication demand rather than a measurement of traffic on every physical link. This thesis primarily reports elapsed time and algorithm bandwidth; payload definitions distinguish per-peer, per-rank, and aggregate sizes where relevant.

\paragraph{Overlap.}
A single-operation model does not locate communication on an application's critical path. If halo transfer and independent local SpMV take $T_h$ and $T_l$, ideal overlap reduces their combined interval from $T_h+T_l$ to $\max(T_h,T_l)$. Real execution adds posting and synchronization costs and may slow either task through resource contention. CPU-assisted progress can sustain this overlap while a GPU computes; conversely, device invocation can still serialize dependent work. The remaining wait after local computation is therefore not the full transfer time, a distinction needed to interpret aCG's phase measurements.

\paragraph{Application-side reference.}
The Roofline model \cite{williams_roofline_2009-1} bounds kernel performance by arithmetic intensity against memory bandwidth and peak throughput. Most kernels in a sparse iterative solver are memory-bound, so a communication speedup matters only to the extent that communication remains exposed after sparse matrix--vector multiplication and vector kernels are included. Models combining a kernel-level roofline with a network model \cite{choi_end--end_2020} are the closest existing analogue to the cross-layer view taken here.

\section{The Leonardo System}\label{sec:leonardo}

All measurements in this thesis were collected on the Leonardo supercomputer at CINECA, specifically on its accelerated Booster partition \cite{turisini_leonardo_2024}. Leonardo ranked 12th in the June 2026 TOP500 list \cite{top500_june2026}. It is used as one concrete production system and is not assumed to represent every contemporary HPC architecture.

Each Booster node is an Atos BullSequana X2135 ``Da Vinci'' blade integrating one Intel Xeon Platinum 8358 processor with 32 cores, 512\,GB of DDR4 system memory, and four NVIDIA A100 SXM GPUs with 64\,GB of HBM2e each \cite{turisini_leonardo_2024}. The GPUs are directly connected by NVLink~3.0 without NVSwitch, with the pair and endpoint bandwidths described in Section~\ref{sec:intra-node}. Nodes connect through an NVIDIA Mellanox InfiniBand HDR network in a DragonFly+ topology with two dual-port HDR100 adapters per node. Jobs are submitted through Slurm.

This configuration provides both communication domains described in Section~\ref{sec:interconnects} within one machine. Single-node and multi-node runs reveal sensitivity to placement and fabric, but they do not isolate topology from algorithmic behavior: libraries may change algorithms, protocols, staging, and progress mechanisms when a communicator crosses a node boundary. The experimental design must therefore report the complete selected stack and interpret each transition as a cross-layer change.

IBGDA is unavailable in the evaluated Leonardo environment, as also reported by Trotter et al.\ \cite{trotter_cpu-_2025}. Direct NVSHMEM therefore uses the \texttt{ibrc} CPU-proxy path for inter-node device requests. Section~\ref{sec:ibgda-check} reports the availability check, Section~\ref{sec:runtime-method} specifies runtime configuration, and Section~\ref{sec:eval-environment} records the software environment.
