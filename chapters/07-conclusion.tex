\chapter{Conclusions and Future Work}\label{ch:m-conclusion}

This chapter closes the investigation of GPU-initiated communication and application scalability. Drawing on the discussion in Chapter~\ref{ch:m-discussion}, it summarizes the contributions and principal findings, and states their implications for selecting communication backends. It then outlines five research directions for extending the evaluation and resolving the questions left open by the current evidence.

\section{Conclusions}

This thesis developed a bottom-up method for locating favorable distributed-GPU communication paths and testing which observations survive composition and complete solver execution. A unified benchmark suite measured point-to-point, halo, allreduce, and all-to-all patterns, then MoE and CG-inspired application microbenchmarks, through CUDA-aware and SYCL-aware MPI, NCCL, oneCCL, NVSHMEM, and OSHMPI, including persistent kernel-invoked NVSHMEM neighbor kernels. The software contributions extend oneCCL with grouped NCCL point-to-point handling, an OSHMPI backend for the benchmarked operation set, and a validated NVSHMEM backend foundation, and extend aCG with an OSHMPI communicator and a SYCL implementation. Together, these five contributions connect interface engineering and controlled communication measurements to two large sparse matrices through 32 A100 GPUs.

Chapter~\ref{ch:m-discussion} answers the three research questions against that evidence. Read together, they give one conclusion: on this platform device initiation is a conditional tool rather than a general improvement. It repays its cost where communication is repeated, regular, and can remain inside persistent device work, which among the measured patterns is the batched multi-node halo and, in the solver, the monolithic variant at larger process counts. Elsewhere a host-driven library remains competitive or better, because the factors that decide the outcome are memory placement, completion semantics, and progress rather than the location of the call. The benchmark evidence transfers to the application only where the operation and its dependencies are genuinely the same; where the application adds irregular peers or overlap, the benchmark bounds the answer rather than predicting it. These conclusions describe configured paths on proxy-assisted networking, not an intrinsic ordering of libraries or an initiation-only speedup.

The preliminary NCCL~2.31.2 study in Appendix~\ref{app:nccl-preliminary} adds a candidate rather than a revised application result. Symmetric buffers improve the supplied small-allreduce medians relative to NCCL~2.18.5, but the advantage reverses at some intermediate sizes and does not extend to small all-to-all. This reinforces the need to record version, memory handling, and selected operation path before interpreting a library upgrade as evidence for GPU initiation.

The resulting recommendation is to select configured paths for a specific application signature. For GPU initiation, developers should first identify repeated communication that can remain inside persistent device work, then verify whether the target transport is GPU-posted or CPU-proxied. They should benchmark the matching pattern and completion boundary, retain several plausible host- and GPU-initiated stacks, and validate them with a composite or complete application whose synchronization and overlap semantics match production execution.

\section{Future Work}\label{sec:priority-experiments}

Five research directions follow from the measured regimes and the attribution limits discussed in Chapter~\ref{ch:m-discussion}.

\begin{enumerate}
    \item \emph{Validation on diverse clusters with GPU-posted networking.}
    Repeat the evaluation on clusters with verified IBGDA support to determine how GPU-posted communication changes the regimes observed under proxy-assisted progress. Where possible, compare proxy-assisted and IBGDA transports on the same hardware, keeping the communication schedule and runtime configuration matched. Verify and record the active transport, GPU/NIC placement, and software versions. Extending the campaign across GPU generations and interconnects would test whether the observed behavior generalizes beyond Leonardo. This separates the effect of removing CPU request posting from differences between clusters, without assuming that the GPU-posted path is always faster.

    \item \emph{Isolation of initiation effects.}
    Compare host-called, host-on-stream, nonpersistent device-invoked, and persistent device-invoked NVSHMEM implementations. Match message layout, memory placement, communication algorithm, transport, signaling, batching, and completion requirements wherever the interfaces permit. Vary persistence and batch length separately, and control collective dispatch and local computational kernels in the host- and device-driven solver variants. These experiments would establish how much of an observed improvement comes from invocation location, persistent execution, or communication--computation fusion.

    \item \emph{Stronger correspondence between benchmarks and applications.}
    Extend the benchmarks to reproduce the solver's directed peer graph, per-peer message volumes, and dependencies between communication and computation. Replay the archived halo graphs with representative local work, sweep batch length, and interleave halo exchanges with computation and reductions. Measure scalar reductions through completion visible to a dependent GPU consumer, including the full device-to-host/reduction/host-to-device round trip for staged OSHMPI. Comparing these measurements with exposed communication time and complete solver time would test which benchmark observations explain CG scalability across additional sparse matrices.

    \item \emph{Evaluation of newer device-communication interfaces.}
    Extend the comparison to recent NVSHMEM releases and NCCL's device API, including intra-node peer-memory operations, supported low-latency collective designs, and inter-node GIN \cite{hamidouche_kernel-initiated_2026,shen_every_2026}. Distinguish improvements due to library version, symmetric-memory registration, collective algorithms, and device-side invocation through matched comparisons. Evaluate direct GPU-posted and proxy-assisted networking where supported, then test whether the observed gains carry over to composite benchmarks and solver execution. This would connect recent device-communication advances to the application dependencies examined in this thesis.

    \item \emph{A device-initiated path behind a portable collective interface.}
    Carry the NVSHMEM backend foundation contributed here \cite{merenda_oneccl_nvshmem_2026} through to a working collective path, then expose device initiation through oneCCL rather than through each vendor library directly, with NVSHMEM's device-side operations and NCCL's device API as the two implementations \cite{uxl_oneccl_2026,nvidia_nccl_device_2026}. The open design questions are where a symmetric window and its registration belong in a oneCCL communicator, how a device-side handle reaches a SYCL kernel without discarding the stream and completion semantics the host interface guarantees, and which part of the operation set can be completed inside a kernel at all. Intel SHMEM establishes that a SYCL-based device-initiated OpenSHMEM implementation is feasible \cite{brooks_intel_shmem_2024}, and the ongoing unification of GPU-aware OpenSHMEM semantics would give such an adapter a stable target \cite{ravi_unified_2026}. Measuring the result against direct NVSHMEM and direct NCCL on the halo, scalar-reduction, and MoE patterns would quantify what a portability layer costs on top of device invocation. The staging penalty measured for the oneCCL/OSHMPI path makes that cost, rather than the device API itself, the decisive question for adapters of this kind.
\end{enumerate}
