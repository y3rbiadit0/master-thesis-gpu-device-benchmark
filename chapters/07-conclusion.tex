\chapter{Conclusions and Outlook}

This thesis developed a bottom-up method for determining where GPU initiation is beneficial in distributed GPU communication and whether that benefit transfers to a complete application. A unified benchmark suite measured point-to-point, halo, allreduce, all-to-all, and CG-inspired patterns through CUDA-aware and SYCL-aware MPI, NCCL, oneCCL, NVSHMEM, and OSHMPI, including persistent GPU-initiated NVSHMEM neighbor kernels. The software contributions extend oneCCL with grouped NCCL point-to-point handling, a complete OSHMPI backend, and a validated NVSHMEM backend foundation, and extend aCG with an OSHMPI communicator and a SYCL implementation. Together, these five contributions connect interface engineering and controlled communication measurements to two large sparse matrices through 32 A100 GPUs.

RQ1 is answered conditionally. GPU-aware MPI remains strongest for startup-sensitive point-to-point and isolated halo communication, so GPU initiation is not a universal latency optimization. Its benefit appears when persistent execution can amortize launch and synchronization: the device-initiated NVSHMEM halo leads the large steady-message region, and the monolithic device-side NVSHMEM solver improves scaling relative to blocking OSHMPI at larger process counts. NCCL-based paths lead large reductions and all-to-all communication, while UCC crosses from harmful to beneficial with size and topology. In \texttt{cg\_step}, NCCL wins the no-communication controls while host-staged OSHMPI wins every multi-rank cell. The lack of IBGDA prevents a direct conclusion about GPU-posted inter-node communication. The winner changes with pattern, size, topology, initiation, completion semantics, memory placement, and runtime configuration.

RQ2 shows that SHMEM's practical value depends on matching its memory and completion requirements to the application. Puts remove per-transfer receive matching but introduce explicit responsibilities for symmetric storage, remote addressing, signaling, and buffer reuse. NVSHMEM supports persistent device execution and stream-ordered communication, while the evaluated OSHMPI path reuses MPI through host-driven, blocking OpenSHMEM operations; their favorable benchmark regimes do not imply the same overlap or solver ranking. A common interface moves some of these responsibilities into an adapter. The new oneCCL OSHMPI backend uses symmetric staging and explicit completion, while the NCCL extension propagates grouped execution so dependent point-to-point batches are correct and usable. The NVSHMEM prototype separately establishes build integration, bootstrap, lifecycle, and symmetric staging, but stops before public collectives and asynchronous event semantics. Source-level interchangeability therefore has concrete memory, synchronization, and implementation costs.

RQ3 connects application transfer with CUDA--SYCL performance retention. Pattern-oriented microbenchmarks predict matched primitives but not automatically a complete application: across two matrices and a 16-fold rank range, the reduction predictions agree with aCG within \mbox{6.5--9.7\%} for MPI and NCCL and \mbox{14--21\%} for matched NVSHMEM, while the regular synthetic halo does not represent aCG's irregular rendezvous exchange or its overlap with sparse matrix--vector multiplication. The \texttt{cg\_step} winner therefore does not remain the aCG winner. The monolithic device-side NVSHMEM solver's stronger scaling trend is consistent with removing repeated host synchronization, but its changed solver organization and CPU-proxied network path prevent attribution to initiation alone. Separately, the reported SYCL solver-time ratios are 1.17--1.45 relative to CUDA MPI on A100 GPUs. This platform-specific comparison measures the time overhead of the portable implementation; supporting compute and orchestration controls help interpret it without isolating the causes of the full solver gap or establishing cross-vendor performance portability.

The preliminary NCCL~2.31.2 study adds a candidate rather than a revised application result. Symmetric buffers improve the supplied small-allreduce medians relative to NCCL~2.18.5, but the advantage reverses at some intermediate sizes and does not extend to small all-to-all. This reinforces the need to record version, memory handling, and selected operation path before interpreting a library upgrade as evidence for GPU initiation.

The resulting recommendation is to select configured paths for a specific application signature. For GPU initiation, developers should first identify repeated communication that can remain inside persistent device work, then verify whether the target transport is GPU-posted or CPU-proxied. They should benchmark the matching pattern and completion boundary, retain several plausible host- and GPU-initiated stacks, and validate them with a composite or complete application whose synchronization and overlap semantics match production execution.

\section{Future Work}

\subsection{Priority Questions for Matched Follow-Up}

The content and evidence review identifies four questions to resolve before broadening the backend matrix:
\begin{enumerate}
\item \textbf{Is the preliminary NCCL gain reproducible, and which path produced it?} Recover the raw logs, exact build/launch commands, \texttt{nccl-tests} commit, allocation/registration flags, and implementation selector; repeat the three configurations with correctness checks and explicit timing boundaries.
\item \textbf{Does the gain apply to the CG primitive and survive integration?} Measure one FP64 sum on two and four GPUs against matched NCCL, MPI, and NVSHMEM paths, then change only the reductions in \texttt{cg\_step} and aCG. Report reduction and complete-iteration costs together with convergence. This avoids interpreting an unspecified 8\,B collective as an already matched result.
\item \textbf{Which advantage follows from initiation?} Compare host-on-stream and device-side variants with the closest feasible algorithm, message layout, completion, and transport settings. Record residual differences rather than attributing a cross-library speedup entirely to invocation location.
\item \textbf{Can a better communication shape or hierarchy improve transfer?} Evaluate irregular halos or local-LSA/inter-node-MPI composition only after the primitive tests. A hierarchical reduction must include local reduction, inter-node communication, local distribution, and the synchronization between them; savings cannot be inferred by combining isolated minima.
\end{enumerate}

\subsection{Broader Experimental and Implementation Work}

The first priority is to improve experimental provenance. Future campaigns should store source revisions, dependency commits, module versions, node names, GPU and NIC identifiers, rank placement, environment variables, and launcher commands in every result artifact. All cells should use the same number of independent allocations, and reports should include job-level distributions and confidence intervals rather than relying primarily on fastest trials.

The communication stacks also require matched sensitivity experiments. The complete aCG host-NVSHMEM campaign should be repeated with NCCL collective dispatch enabled. UCC's 4\,KiB k-nomial-to-SRA-k-nomial boundary is now identified, but forcing alternatives around that threshold is still needed to determine whether the default can be improved. GPU Direct paths and CPU/NIC affinity should be recorded and varied independently; the UCX rendezvous-threshold and rail-count questions are closed for the present production setting. The anomalous single-rank allreduce control should be repaired and retained as the no-communication baseline. A clean all-to-all campaign under the new default is still required, as is the first measured MoE campaign; the current all-to-all tree merges two result sets and MoE has not been measured.

The most important missing communication shape is an irregular halo generated from a real sparse partition, with rank-dependent neighbor counts and per-peer message sizes. It should reproduce the observed 1.0--10.8-neighbor range and 125--336\,KiB volume per iteration, while reporting job-level distributions so that the MPI fast and slow regimes can be localized. The residual SYCL cost should be separated by comparing \texttt{sycl::reduction} with the hand-written dot kernel and by measuring queue-submission cost directly. NVSHMEM's 1.29--1.68-fold scale-dependent spread likewise requires CPU-affinity and proxy-progress experiments rather than another aggregate mean. OSHMPI's growing isolated-versus-steady first-touch cost should be measured separately for irregular peer sets. The existing \texttt{1n1g} \texttt{cg\_step} control should also be retained and repeated for both OSHMPI reduction-memory modes: without inter-rank communication or RMA traffic, it can isolate whether the 45--47\% compute increase follows the symmetric allocator rather than UCC communication.

For OSHMPI, the next implementation step is a genuinely nonblocking halo protocol using \texttt{shmem\_putmem\_nbi} in the begin phase and a deferred \texttt{shmem\_quiet} in the end phase. Instrumentation should separate CPU issue time, network progress, and exposed wait before and after the change. Neighbor-only completion should be revisited only after these components are measured. The oneCCL/OSHMPI backend should also evaluate its direct-buffer path against conforming symmetric staging and add robust support for communicator subteams where the OpenSHMEM team lifecycle permits it. The oneCCL/NVSHMEM prototype must first complete dependency import, returned-event semantics, same-team stream ordering, and the initial barrier, allgather, allreduce, all-to-all, and broadcast mappings. Only after those host-enqueued operations are correct and measured should a kernel-initiated path be added and compared against direct NVSHMEM and the existing oneCCL backends.

Direct GPU-posted networking remains an important extension, but the evaluated NVSHMEM~2.11.0 configuration cannot establish its performance. A site-supported experiment would need compatible driver settings and a verified active IBGDA path; a newer NVSHMEM release may provide other NIC-handler configurations whose requirements must be checked independently. Merely enabling \texttt{NVSHMEM\_IB\_ENABLE\_IBGDA} while retaining the explicit \texttt{ibrc} selection is insufficient. Host-on-stream, device-side, and monolithic solver variants should be compared under matched collective settings. For NCCL, recover the stalled run's diagnostics and check the exact release's GDAKI prerequisites before attributing failure to the NVSHMEM driver issue. The preliminary symmetric-window timings motivate further intra-node work, but a user device-API experiment must explicitly establish invocation mode and separate LSA from network GIN behavior.

Finally, the evaluation should extend beyond Leonardo. Repeating the methodology on AMD and Intel accelerators with RCCL, ROC\_SHMEM, Intel SHMEM, and appropriate MPI implementations would test whether the observed decision boundaries generalize. Additional sparse matrices, pipelined CG, larger GPU counts, and a real redistribution-heavy application for the all-to-all benchmark would broaden application validity. A longer-term goal is to turn the measured decision surface into a tool that accepts an application's communication signature and recommends a small set of backend configurations for confirmatory testing.
