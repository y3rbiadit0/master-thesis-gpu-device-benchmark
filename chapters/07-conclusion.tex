\chapter{Conclusions and Future Work}\label{ch:m-conclusion}

This chapter summarizes when GPU-initiated communication helped in the experiments and what the benchmark results imply for application-level stack selection. It then outlines five research directions for testing these conclusions on other systems and separating the effects that changed together in this study.

\section{Conclusions}

This thesis developed a method for comparing GPU communication stacks and checking whether their benchmark performance carries over to an application. A unified suite measured point-to-point, halo, allreduce, and all-to-all patterns, followed by MoE and CG-inspired application microbenchmarks. The comparison included CUDA-aware and SYCL-aware MPI, NCCL, oneCCL, NVSHMEM, and OSHMPI, with persistent NVSHMEM kernels for neighbor exchanges. The software contributions extend oneCCL with grouped NCCL point-to-point support, an OSHMPI backend for the benchmarked operations, and a validated NVSHMEM runtime foundation. They also extend aCG with an OSHMPI communicator and a SYCL implementation. Together, these five contributions connect library integration and communication measurements to solver tests on two large sparse matrices using up to 32 A100 GPUs.

The results show why keeping repeated work on the GPU can help, and why it is not enough on its own. Persistent NVSHMEM performs well for batched multi-node halo exchanges. In the solver, the monolithic device-initiated variant improves relative to blocking OSHMPI as more GPUs are used, but remains behind NCCL. Host-driven implementations can still be faster when their algorithms, memory handling, and synchronization fit the workload better. These comparisons measure all of those choices together on a system with proxy-assisted networking; they do not isolate the effect of moving the communication call onto the GPU.

The benchmark-to-application comparison reaches a similarly practical conclusion. Matched scalar reductions and comparable local work produce useful agreement, while irregular peers and overlap can change the ranking. Benchmarks help narrow the choice of stack, but the final comparison must account for the application's computation and the points where it waits for communication.

The preliminary NCCL~2.31.2 study in Appendix~\ref{app:nccl-preliminary} suggests a further experiment. Symmetric buffers improve the small-allreduce medians relative to NCCL~2.18.5, but the advantage reverses at some intermediate sizes and does not extend to small all-to-all. An application-level test would need to record the version, memory handling, and invocation method before attributing any improvement to GPU initiation.

The practical outcome is a sequence of steps for choosing a communication stack for an application on a particular system:

\begin{enumerate}
    \item \emph{Compute patterns.} Identify the local work per GPU and where it depends on remote data. The device-initiated step reproduced the solver's scaling at one grid side and missed it at another, showing that the ratio of computation to communication matters when choosing a representative benchmark.
    \item \emph{Communication patterns.} Identify the operations, peers, message sizes, and points where the application needs their results. The MoE routing cases show that changing the payload distribution can reverse a ranking even when operation and total volume stay fixed.
    \item \emph{Cluster capabilities.} Check the local and network interconnects, whether GPUs or CPU proxies post network requests, and which library versions and settings are installed. On Leonardo, NVSHMEM lost ground in most patterns when communication crossed nodes; proxy overhead is one possible contributor that needs a matched test.
    \item \emph{Candidate libraries.} Select host- and GPU-initiated stacks that perform well for the relevant patterns, payloads, and topologies. Carry several candidates into application testing, since the fastest isolated operation may not produce the fastest solver.
    \item \emph{Performance gains and losses.} Compare the candidates first in an application microbenchmark and then in the application itself. Require each result to be ready in the same memory location for the next computation, and reproduce the application's synchronization and overlap. Report slowdowns as well as improvements.
\end{enumerate}

This procedure follows the evaluation used here, which covered one solver and one routed-exchange microbenchmark on one system. Its usefulness for other applications and clusters remains to be tested.

\section{Future Work}\label{sec:priority-experiments}

Five research directions follow from the performance differences and unresolved causes discussed in Chapter~\ref{ch:m-discussion}.

\begin{enumerate}
    \item \emph{Validation on diverse clusters with GPU-posted networking.}
    Repeat the evaluation on clusters with verified IBGDA support to determine which message sizes and workloads benefit from GPU-posted communication. Where possible, compare proxy-assisted and IBGDA transports on the same hardware, keeping the communication schedule and runtime configuration matched. Record the active transport, GPU/NIC placement, and software versions. Tests across GPU generations and interconnects would show whether the behavior observed on Leonardo also occurs elsewhere. Matched measurements are needed to distinguish the effect of removing CPU request posting from other differences between clusters.

    \item \emph{Isolation of initiation effects.}
    Compare host-called, host-on-stream, nonpersistent device-invoked, and persistent device-invoked NVSHMEM implementations. Match message layout, memory placement, communication algorithm, transport, signaling, batching, and completion requirements wherever the interfaces permit. Vary persistence and batch length separately, and control collective dispatch and local computational kernels in the host- and device-driven solver variants. These experiments would establish how much of an observed improvement comes from invocation location, persistent execution, or communication--computation fusion.

    \item \emph{Stronger correspondence between benchmarks and applications.}
    Extend the benchmarks to reproduce the solver's directed peer graph, per-peer message volumes, and dependencies between communication and computation. Replay the archived halo graphs with representative local work, sweep batch length, and interleave halo exchanges with computation and reductions. Measure scalar reductions through completion visible to a dependent GPU consumer, including the full device-to-host/reduction/host-to-device round trip for staged OSHMPI. Comparing these measurements with exposed communication time and complete solver time would test which benchmark observations explain CG scalability across additional sparse matrices.

    \item \emph{Evaluation of newer device-communication interfaces.}
    Extend the comparison to recent NVSHMEM releases and NCCL's device API, including intra-node peer-memory operations, supported low-latency collective designs, and inter-node GIN \cite{hamidouche_kernel-initiated_2026,shen_every_2026}. Distinguish improvements due to library version, symmetric-memory registration, collective algorithms, and device-side invocation through matched comparisons. Evaluate direct GPU-posted and proxy-assisted networking where supported, then test whether the observed gains carry over to composite benchmarks and solver execution. This would connect recent device-communication advances to the application dependencies examined in this thesis.

    \item \emph{A device-initiated path behind a portable collective interface.}
    Add device initiation to a portable collective interface such as oneCCL, using NVSHMEM's device-side operations and NCCL's device API as alternative backends \cite{uxl_oneccl_2026,nvidia_nccl_device_2026}. Three design questions remain. How should a oneCCL communicator manage symmetric windows and their registration? How can it pass a device handle to a SYCL kernel while preserving the host interface's ordering and completion guarantees? Which operations can finish entirely inside the kernel?

    Intel SHMEM demonstrates the feasibility of device-initiated OpenSHMEM operations in SYCL \cite{brooks_intel_shmem_2024}. Work on unified GPU-aware OpenSHMEM semantics could provide a common target for such an adapter \cite{ravi_unified_2026}. Comparing it with direct NVSHMEM and NCCL on halo, scalar-reduction, and MoE patterns would measure the added cost of the portable interface. The oneCCL/OSHMPI staging results show why managing buffers and completion efficiently is central to that design.
\end{enumerate}
